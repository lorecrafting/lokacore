## What must be true (from the spec, before the diff)

1. An item has exactly one authoritative container (a room, an actor's body, an NPC or an
   item); inventory and room contents are derived from it, never stored (03 §23; 21 §8).
2. Take, drop and give are conserved transfers: custody checked against the overlay, no
   containment cycle, destination capacity respected, all on the real decision path; a
   violation discards the whole proposal (04 §5.1, §5.3; invariants `one_container_per_item`,
   `containment_acyclic`).
3. A `fact.assign` whose fact, scope or value its FactSpec does not allow fails the decision
   before persistence, and nothing commits (03 §7; 04 §5.1 final validation).
4. Each executed `fact.assign` that changes its value yields one `fact_changed` (old, new,
   the fact's scope) at its causal position in the decision's FIFO, owned by fact@1; an
   unchanged value yields none (03 §7; 04 §5.2 steps 4-6; owner decision Q2 as clarified).
5. Rules take the actor from the command; only one lookup assumes one body (puppeting lesson).
6. Touch links live in catalog strings (`Text` stays `{key, bindings}`); an unresolved target
   is an error, a missing link a warning; GameView's contract is unchanged; players read plain
   words (owner decision Q3).
7. New source reference fields are expanded by `Checks.expand/2`; the format tag stays
   `loka-cartridge-v2`; installed artifacts and frozen known answers are unchanged.

## Findings

1. **should-fix: `fact_changed` goes after all of the rule's events, not at the assign's
   causal position.** `kernel/ts/src/world.ts:212` sets `position = decision.events.length +
   i + 1`, and `kernel/ts/test/facts.test.ts:240` treats "before the rule's events" as a
   break, which freezes that order. Today no rule proposes `fact.assign`, and there is no
   subscriber delivery until reactions (R7/R8), so nothing observable differs yet. The first
   proposer is S5's ActionRecipe. Failure scenario: a recipe whose explicit sequence is
   `fact.assign bell_rung; emit bell_heard` puts `bell_heard` ahead of `fact_changed` in the
   FIFO. Under 04 §5.2 steps 4-5, the subscribers to `fact_changed` should see the fact change
   first, and a reaction with a lifecycle guard can then see a different eligibility set at
   that position. A rule result is `{delta.ops, events}` and cannot express interleaving, so
   the order cannot be fixed here without changing the Rule contract. Minimal fix: put a
   `ponytail:` comment in `adopt` saying the position is "after the rule's events until a
   rule result carries one ordered sequence (S5 ActionRecipe)". Also drop "before the rule's
   events" from the test's break list, so S5 is not held to the wrong order. The adopt
   docstring and the PR body say "after the rule's events" openly, so this is a gap in the
   record, not a hidden deviation.
2. **should-fix: `has_item`'s see-through semantics are not in the contract.**
   `protocol/policy.schema.json:120` says only "The actor holds an item of this definition."
   `kernel/ts/src/policy.ts` counts an item inside anything the body holds, however deep. The
   spec is silent: 21 §8 and 06 §21 name the op, and 03 §23 makes characters and chests
   containers. The choice is consistent with them and changes no frozen answer, because
   `has_item` was not evaluated before this PR. But the contract is what a second
   implementation reads. Failure scenario: the Elixir host, when a server first consumes this
   capability (ADR-074), implements "holds" as direct custody. After `take satchel` in
   `ashmere_items` (the oil is inside the satchel), the two kernels then choose different
   lantern room lines (`item.lantern.room_oil` against `item.lantern.room`). Fix: one clause
   in the description, for example "directly or inside an item it holds, at any depth", then
   `elixir bin/contracts.exs`.
3. **nit: the budget gap is recorded only in the PR body.** Appended `fact_changed` events are
   not counted in `admit`'s `output_bytes` check, and the note exists only in the PR body.
   The `ponytail:` comment at `kernel/ts/src/world.ts:235` names only fixed-size results.
   Failure scenario: the S5 recipe that sets many facts passes `admit` under the limit and
   then grows past it in `adopt`. Add the gap to that comment so S5's size test covers
   `adopt`'s output.

## Question

- **Q1 (`kernel/ts/src/rules/containment.ts:53`).** `give` accepts only a recipient of
  definition kind `npc`, while the brief says "another actor". This is correct today: the one
  player body is not in `world.entities`. When admission accepts a second actor (puppeting,
  multiplayer), giving to a player's body would be `invalid_target`. Should the puppeting line
  in the contract lessons list this check next to `bodyOf`?

## Developer's open decisions (PM leans accept all)

I agree with all four. None is wrong.

- **containment owns the `npc` definition kind.** Fine for now. Moving it later to its own
  capability is a registry change that changes what a cartridge with NPCs must require and
  lock, so settle it before a bundled chapter ships NPCs (R6P).
- **`{"in": "room", "room": ...}` locations.** This matches the short-refs decision: the field
  names the kind, so a short ref is never ambiguous. The new `expand/2` clauses are guarded
  (`is_map_key`, `is_binary`), so a detail keyed `in`, `room` or `room_line` does not match
  them. This is the S3 `exits` crash class, checked.
- **`ashmere_details` and `ashmere_facts` keep their link warnings.** The ruling says "where
  cheap". Adding links would change frozen known answers and three transcripts, and the
  hand-listed warnings are the regression test for the warning path.
- **`implemented_in` stays `r3_pr5`.** Correct: `compose` has enforced both invariants in both
  kernels since R3 PR5. S4 connects capacities to that check and does not implement the
  invariants anew.
