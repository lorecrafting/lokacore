## Must be true (written before the diff)

1. `nonfuture_job`: a schedule inside a job's run (and its reactions) is checked against that job's due time, a root or root-reaction schedule against the target, and a job scheduled due by the target completes in the delta. Both kernels fault the same target.
2. In-advance scheduled jobs run in `(due_time, job_id)` order among the pending set; no insertion-order leak.
3. Only strictly earlier-due groups merge; equal-due writes still fault `conflicting_write`; root and reaction writes in one wait behave as in step 1 of the split.
4. A job's preconditions read the overlay the same way the committed state of the stepped version would.
5. No device clock; no mechanic named in `proposal.ts`.

1, 2, 3, 5 hold at head. 1 holds in the code but its Elixir half has no red control (finding 1). 4 holds for job rules (`now(p)` replays the advance from the base clock, `proposal.ts:120-135`); a rule reading `world.state.clock` inside a run sees the target in both the long wait and the stepped version's last step only if its due time is the step end, which the host boundary guarantees (`mechanics.md` known limit).

## Answers to the PM's questions

1. Precision: ambiguity in finding 2 only. Everything else is byte-determined: `(due_time, job_id)` order, code-point key order for the final check, choice limit before `nonfuture_job`, `job.complete` sets the time and `job.cancel` does not.
2. Equivalence: no new divergence found. Equal-due writers fault in both forms (mutant B's red controls cover the one-wait side; the stepped side runs both jobs in one step). Reactions of a run are joined before `joinTail`, so a reaction write to a strictly earlier run's target joins in one wait as it does across steps (boss reaction-write test). Status sub-steps and encounter rounds: `currentRound` and `statusGroup` read `now(p)` with the advance replayed, the same rows a step would commit. Known limits stand as accepted.
3. Determinism: `enqueue` sorted insert and `cmp` (code point) in TS; `Enum.sort` on the overlay in Elixir (byte order; ids and target keys are ASCII, so equal). `merge` relabels by value, so `new Set` iteration in `joinTail` only orders independent merges. No insertion-order read remains in the final checks.
4. Merge readiness: FD1 merges cleanly in principle (`runDelayed` emits `job.complete` first, so `times` and `joinEarlier` treat it like any run); the clamp removal is unsafe for root-delivered delayed reactions (finding 3) until root schedules are queued.
