## What must be true (from the spec, before the diff)

1. Actions compose from sources by the five ADR-016 operations with the stable action key
   as identity; policies are evaluated after composition; lists sort by priority (06 §19).
2. A recipe is compiled, immutable, schema-validated, bounded and deterministic, built only
   from registered typed operations: no untyped effect list, no generic setter (06 §20; 21;
   05 §28).
3. The authority re-resolves the advertised action to the compiled recipe and runs it
   through the normal Command/decision path as one logical decision; a client cannot invoke
   an action its current set does not offer (06 §20; 21; ACT-09).
4. Content emits only its own declared custom events and cannot forge an engine-owned event;
   unknown operations and event types fail validation (04 §5.3; 05 §28).
5. The root sequence's order is semantic: each event at its causal position, so
   `assign X; emit Y` yields `fact_changed(X)` before `Y`; an unchanged value yields none;
   the output budget covers everything the decision emits; a fault discards the whole
   proposal (04 §5.2 steps 4-7, §5.4).
6. The frozen shape takes the rest of 21's list (costs, Check, result bands, cooldown,
   typed consequences, NarrationSpec) as additions, without a format break.
7. Touch and terminal reach the same semantics (ADR-016).

## Composes-with (reviewer step 7)

The statement is accurate. Recipes read facts, containment (`has_item`), the actor's room and
details, and write only through `fact.assign` (typed, `fact@1`) and the recipe's own
`custom_event`. Description variants and `fact_changed` subscribers pick up a recipe's
change with no extra code. Capability code names no content. One place names other
mechanics: `VERBS` in `actions.ts` (N1). The developer disclosed it, and the contract lesson
records it.

## Findings

**F1 (should-fix): one action key can have two definitions, and the loader never checks.**
`lib/loka/content/recipes.ex:39-41` rejects a recipe that shares a cartridge *action's* key,
but not one that shares an engine verb's key, and `kernel/ts/src/cartridge_refs.ts:142-175`
(the loader) checks neither. `actions.ts:94-106,121` then lets the recipe override. Failure:
an author writes `recipes/look.json` (for example "look through the telescope"). It compiles
with no diagnostic (probed: `{:ok, []}`). From then on every `look` Command, including
examine, is refused `unsupported_capability` in every room of the cartridge, because the
set's `look` entry is now a `perform` recipe. The GameView advertises `look` only in the
recipe's room. The same happens with `take`, `move`, `drop` and `give`. Separately, an
artifact with an action and a recipe of one key loads (probed), and the action silently
disappears. The loader is the install trust boundary (AGENTS.md: never simplify away
validation there), and here it accepts an artifact the compiler would never emit. Fix: report
`DUPLICATE_DEFINITION` for a recipe whose key is a registered command or an action of the
cartridge, in both the compiler and the loader. That is a few lines next to the existing
contribution-key check, with a red case each, and it also closes the PM's loader question.

**F2 (should-fix, needs a PM decision before the freeze): `action_completed` and the
`action_recipe@1` event stream.** 00a Q3 makes the chapter's objective
`event: { type: action_completed, action: ring_bell }`. This slice freezes a successful
`perform` as emitting exactly the sequence's events
(`cartridges/ashmere_bell/transcripts/action_recipe.jsonl`, `rules/action_recipe.ts:36`).
Failure: if R7 adds `action_completed` to `perform` under `action_recipe@1`, the same
cartridge at the same capability version commits a different event list and positions. That
silently changes an existing lock, which 04 §5.2 forbids. If R7 has quests subscribe to
`custom_event` instead, it departs from 00a, and objectives then depend on each recipe's
author remembering an `event.emit` step. My recommendation: `action_recipe@1` emits an
engine-owned `action_completed {action, subject_id}` after the sequence. It is keyed by the
stable action key, content cannot forge it, and it is what 00a names. It costs one registry
event and one line in the rule. Leave `custom_event` for ReactionRules. If the PM prefers to
defer, record now that adding it is `action_recipe@2`.

**N1 (nit, composes-with): engine verbs are a table in `actions.ts`.** `actions.ts:67-75`
names five other capabilities' verbs and their target and input specs, and `step` admission
now depends on the table. The next capability with a player verb (dialogue's `talk`,
schedule's `wait`) is refused `unsupported_capability` until someone edits `actions.ts`. The
contract lesson records this. Add a `ponytail:` note at `VERBS` naming the upgrade: move
target and input onto the command's registry entry when the next verb capability lands. That
slice must also decide how continuation responses (`choose`, `close_choice`) are admitted,
since they are not ActionSet actions.

**N2 (nit): inconsistent codes for a subtracted action.** `actions.ts:144`: a room that
subtracts an engine verb refuses it `unsupported_capability`, but one that subtracts a recipe
refuses `perform` with `not_found` (probed). The recipe exists; it is just not offered here.
Use `unsupported_capability` for a recipe key that exists in the cartridge but not in the
set, and keep `not_found` for an unknown key.

**N3 (nit): the transcript was captured from a dirty tree.**
`cartridges/ashmere_bell/transcripts/action_recipe.jsonl` records
`loka-kernel@0f5afff…-dirty`, so its `kernel_version` names no commit that produced it. Every
earlier transcript has a clean commit. Re-capture from a committed tree.

## Questions

**Q1: "declared" custom events.** 04 §5.3 says content may emit only *declared* custom
events. This slice counts the recipe's own `event.emit` step as the declaration and defers
an `events` map to R8. That reading is defensible, since the namespace makes forgery
impossible. But if R8 then requires every emitted key to be in the map, an installed v2
artifact without one stops loading. Recommend recording now that R8 treats an absent
`events` map as "the keys the recipes emit". The alternative is to make the map required
only under a new tag.

**Q2: observers' narration.** Compiling and validating `observers` without emitting it is
right for a private world with no second viewer. The Realm host that first has observers must
emit it at commit, as the schema text already says. No change requested.

Answers to the PM's other points: `perform` as a generic Command is spec-conformant (item 3).
A recipe cannot impersonate an engine event or write outside `fact.assign` on its own facts
(item 4). `fact_changed` ordering and the budget are correct and tested against the old
order (item 5). The short-ref expansion for the new ref fields is covered and does not crash
on malformed input.
