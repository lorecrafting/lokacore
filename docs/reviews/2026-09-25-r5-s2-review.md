## What must be true (from the spec, before the diff)

1. Details are an optional, additive room field: a room without `details` compiles, loads and
   hashes exactly as in S1; the `loka-cartridge-v2` tag stays (S1 F3/A7 compatibility rule).
2. A detail has aliases and a description text key (21 §6); the compiler and the loader both
   check the key against the catalog, as they do for rooms and actions.
3. Detail target ids are IdSource ids under the nil CommandId, appended after the rooms in a
   reviewed order that does not depend on JSON key order; the rule is written into the numeric
   profile, and a known answer is computed outside the kernels.
4. Resolution is deterministic `none | unique | ambiguous(candidates)`, no random tie-break,
   candidates in a fixed order (21 §7); scope is the actor's room (04 §18); one Search, no
   transport-specific lookup helper.
5. Resolution happens before a Command exists (04 §17): only a resolved id enters the Command;
   the player's words never do (ADR-075 §6 A5). None and ambiguous produce no Command, no
   `trace.command`, no ordinal.
6. The failed lookup goes to `diagnostics` under `RunIds`, never `game_trace`; each word is
   `[a-z0-9]{1,32}` or `redacted`, decided before the record is built; a schema-valid leak (a
   serial, a user name) is tested and stripped (ADR-075 §6, §7).
7. `look` with a `target_id` re-validates it in the rule (a stale or foreign id is a rejection,
   never a crash); `look` without one is unchanged and S1 transcripts still replay byte for byte.
8. `target.unresolved` is registered with its first producer: registry entry, record branch,
   data contract with examples and invalid fixtures, every `required` and bound with a fixture
   that fails when it is removed (contract lessons).
9. Every new check has a planted case that fails (feature map: stale file, implemented
   capability without cells; Admitted brand: `tsc` rejects `step` without `admit()`).
10. Tests: expected values from Python or hand-written tables, never from the kernel; the
    frozen S1 fixtures are untouched.

## Findings

- **F1 (should-fix) `kernel/ts/play/obs.ts:78-81` (`lookupWords`: `pieces`, `hidden`)**: the
  word redaction keys on every letters-and-digits piece of every path in `secrets` (`ROOT`,
  `process.cwd()`, `homedir()`, `tmpdir()`), not on host identifiers. Reproduced on this host with
  the details artifact: `look users`, `look folders`, `look private` are recorded as
  `{"kind":"redacted"}`; on GitHub Actions (`/home/runner/work/lokacore/lokacore`) `look home`,
  `look work` and `look runner` would be. Failure scenario: a tester in the Lab types `look home`
  (a plausible content gap); the diagnostics record shows only `redacted`, so the signal the owner
  asked for ([decision](../decisions/owner-decision-lab-failed-lookups-2026-09-25.md)) is lost
  silently, and no test notices because `post` survives. A lookup word can only match
  `[a-z0-9]{1,32}`, so no path can ever be a word; the pieces that matter are the user name, the
  hostname's labels and `ANDROID_SERIAL`. Building `pieces` from those three alone is both correct
  and shorter. Add `look home` (or any word that is a piece of `ROOT` on the running host) to the
  serial/user-name test so the over-redaction has a check. Not a blocker: the record is
  schema-valid and leaks nothing; it is lossy where the owner wanted signal.
- **N1 (nit) `lib/loka/content/checks.ex:113`**: `Enum.sort(ds)` is redundant.
  `Loka.Content.sorted/1` (`content.ex:58-61`) sorts every diagnostic by path, code and bytes
  before it leaves the compiler, and maps of at most 32 keys iterate sorted anyway (contract
  lessons), which is why mutant E5 survives 11/11. Delete the sort.
- **N2 (nit) `kernel/ts/play/main.ts:100`**: `command(r, parsed: object)` replaced the
  `Exclude<Parsed, string | null>` type; any object now spreads into a Command payload, so a
  reordering of the two `else if` branches in `session` (`main.ts:68-69`) that sent
  `{ lookup: 'post' }` to `command()` would compile. `line()`'s schema validation would still
  throw at runtime, so this is a lost compile-time guard, not a hole. A payload type
  `Exclude<Parsed, string | null | { lookup: string }> | { type: 'look'; target_id: EntityId }`
  keeps it.
- **N3 (nit) `docs/features.gen.md` rows `inspectable_detail@1`, `target_resolution@1`**: the
  cell says `not yet` while the TypeScript column lists `kernel/ts/src/target.ts` and the player
  can look at details today. Failure scenario: a PM reads the map and plans "implement target
  resolution" for S3. A reader needs to know the rule (decision 5) to read the row correctly; one
  phrase in the generated header ("`not yet` means no rule module yet; a module in the TypeScript
  column is partial work") or a `partial` cell would do.
- **Q1 (question) `kernel/ts/src/cartridge.ts:231`, `checks.ex:133`**: the `typable` check
  flags a first alias whose first word is `at` even though `look at at post` would reach it
  (`normalize` drops one `at`, then one article). Conservative and consistent in both
  implementations; fine as is, recorded so nobody "fixes" one side alone.

## The six developer decisions

1. **Detail target ids allocated after room ids: agree.** Rooms keep the S1 ordinals, so adding
   details to a cartridge never renumbers a room; details follow in room order then key order
   (UTF-8 bytes), which the shuffled-keys test pins and Python reproduces. The numeric-profile
   amendment states the rule and that ids belong to one artifact and one world. The cost is
   inherent to any counter scheme, not to this order.
2. **Resolution before any Command; none/ambiguous build none: agree.** This is document 04 §17
   literally (parse, Search resolves ids, then the Command) and closes the A5 gap for good: the
   Command carries an id, the words stay in the host. A failed lookup is not a decision, so it
   takes no ordinal and cannot perturb replay. The rule re-validating `target_id` (`not_found`,
   `not_present`) keeps the authority honest against a crafted or stale Command; mutant M6 shows
   the test holds it.
3. **`target.unresolved` in `diagnostics` with `after_ordinal`: agree.** It is a content gap
   (something to fix), not a trace of a decision, so `diagnostics` is the right store and
   `game_trace` stays pure replay input; the schema's `store` enum and fixture make the wrong store
   fail. `RunIds` plus `after_ordinal` is enough to place it between two commands of the run; two
   lookups after the same ordinal are ordered by the file, which is fine for the Lab. See F1 for
   the one thing that undercuts its purpose.
4. **A detail's first alias must be unique and typable: agree.** The first alias is the name the
   host uses in "Which do you mean", so a player must be able to type it and get exactly that
   detail; otherwise the disambiguation prompt names something unreachable. Shared later aliases
   staying legal (`post` on both the notice and the mooring post) is what makes ambiguity
   testable at all. Both compilers enforce the same predicate (E1-E4, M7-M8 all die).
5. **Feature map: implemented = rule module exists: agree with a reservation (N3).** It is the
   one definition a script can check without judgment, and it lines up with `INSTALLED`, which is
   built from `RULES`: a capability without a rule module cannot be locked by any cartridge, so
   it is not shippable however much code exists. The reservation is presentation: the map now
   says `not yet` beside working code, and the header should say what the cell means.
6. **`inspectable_detail` lock requirement deferred to S3: agree, with the cost named.** With
   `INSTALLED` derived from `RULES`, a cartridge that required `inspectable_detail@1` today would
   fail `CAPABILITY_NOT_INSTALLED`, so requiring it needs a rule module (or a change to
   `INSTALLED`) first; S3 is the right place. The cost: when S3 adds the requirement,
   `ashmere_details`'s manifest and lock change, so its content hash, the
   `cartridge_details_hash.json` known answer and both example transcripts must be regenerated.
   That is a few minutes of Python and `loka play`, not a design problem, but the PM should
   budget it in S3's brief.

## Verdict

**APPROVE WITH NOTES.** Every requirement in the list above is met and holds under mutation: the
detail ids and both hashes reproduce outside the kernels, resolution is exact-match, room-scoped
and ordered, no failed lookup becomes a Command or a trace entry, the new contracts have no
fixture survivors, and the two new checks and the brand each fail on their plant. F1 is a
should-fix because it loses the signal the owner asked for on ordinary words; it is a
three-line change with one added test line and can land as a fix round or as the first line of
S3's brief at the PM's choice. N1-N3 are at the developer's discretion.
