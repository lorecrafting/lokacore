## What must be true (from the spec, before the diff)

1. A barrier's state has one owner, barrier@1. It changes only by a registered delta op that
   names a legal transition from the current state. Content cannot write it any other way (04
   §5.3 Lifecycle transition: "only owner capability changes its internals").
2. Composition: in one writer group, legal transitions chain (unlock then open). Writes from two
   groups to one barrier conflict. A `from` that is not the overlay's current state faults. Both
   kernels give byte-identical results, held to hand-derived fixtures (04 §5.1, §5.3).
3. The two faces of one door read one state (21 §5 Barrier; 05 §25). The compiler rejects
   contradictory faces, and the loader rejects exactly what the compiler rejects.
4. An illegal transition, or a move through a closed or locked exit, is a rejection with a
   stable code. It draws no RNG, moves no time and changes nothing (04 §5.0, §7).
5. The GameView marks an exit unavailable exactly when a move through it would be refused, and
   both use one read-only function (04 §15, §19; S6b lesson).
6. Formats are additive. The tag stays `loka-cartridge-v2`, and an exit without a barrier means
   what it did. barrier@1's commands, event and policy leaf are registered now, and no earlier
   artifact can lock barrier@1 (it was not installed), so no frozen event stream changes.
7. `barrier_state` is a policy leaf owned by barrier@1, and it is fail-closed without that
   capability in the lock (06 §21; the S6a versioning rule).
8. Brief mode is presentation only: title and contents on a revisit this session, everything
   on `look` and on a first visit (00 §4.1; owner Q1b; PM ruling).
9. Every cartridge stays playable: the key for each locked door can be reached.

## The developer's decisions, judged against the spec

- **One event `barrier_changed {barrier, from, to}`**: sound. from and to name the transition
  uniquely, and the envelope carries the causing command. It follows the `fact_changed` pattern.
  It is frozen with barrier@1's first installable version.
- **`exit_closed` beside `exit_locked`**: 04 §7's list ends in "...", so it is open to extension.
  The code is registered in `error_registry.json` and the ErrorCode enum. The two causes call
  for different player actions (open versus find the key), so one code per distinct cause is
  right.
- **Three states open, closed and locked**: 21 §5 lists open/closed and locked/unlocked as two
  axes. Their fourth combination (open and locked) has no meaning for a door. One enum with four
  legal edges is the smallest encoding. Damaged and blocked join later as optional fields, as
  BarrierDefinition's description says.
- **Commands carry only a direction**: consistent with 04 §17-§18. The command carries the
  resolved exit, never the player's words. See Q1 for container locks.
- **Both faces name the same barrier or none (BARRIER_MISMATCH)**: this implements 05 §25's
  SHOULD strictly. The spec's "unless explicitly declared independent" escape is deferred with
  a `ponytail:` note. Loosening a check later accepts a superset, so the deferral costs nothing.
  See N2 for a false positive.
- **Brief mode on by default, visited set in the play session**: matches the PM ruling and the
  owner's summary. It has the `ponytail:` note naming map discovery.
- **`size: allow 315` on `lib/loka/core/compose.ex` (312 lines)**: I agree a split would be
  worse. The module is the Elixir twin of `kernel/ts/src/compose.ts` (280 lines, one module).
  The extra length is the moduledoc that documents the composition state's sections. Splitting
  one op family into another module would break the side-by-side reading that parity review
  depends on. The marker is within 1.5x and not stale.
- **Keys that break on a failed force, deferred**: allowed by the brief. It needs a recipe step
  that runs barrier@1's transition logic, plus item destruction.

## Findings

No blockers, no should-fix.

**N1 (nit): TypeScript `compose` throws, where Elixir faults, on a base state whose barrier
state is an `Object.prototype` name.** At `kernel/ts/src/compose.ts:167`,
`(DOOR[op.from] ?? []).includes(op.to)`: with `barrier_initial` (or `barriers`) holding
`"toString"` and an op `from: "toString"`, TS throws "includes is not a function", and Elixir
returns `precondition_failed` (probed). Through `step` this cannot happen, because every stored
or initial state is a schema-checked BarrierState. It is the S6b N1 pattern: the kernels differ
only on malformed composition input. `Object.hasOwn(DOOR, op.from) &&` makes TS fault too.

**N2 (nit): BARRIER_MISMATCH pairs every exit that leads back, not the reciprocal face, so two
separate passages between the same rooms cannot both exist.** See
`kernel/ts/src/cartridge_refs.ts:220` and `lib/loka/content/barriers.ex:38`. Failure: room A's
`north` goes to B through door D, B's `south` goes back through D, and B's `down` is a chute to
A with no barrier. Both kernels report BARRIER_MISMATCH at A.north and B.down, so the author has
two workarounds. One puts D on the chute, which is wrong: closing the door then closes the
chute. The other adds a filler room. Pairing by the opposite compass direction, or accepting a
back exit with no barrier, would fix it. Both are one-line changes in each kernel. Loosening
the check later is compatible, so this can wait for the first map that needs it.

**N3 (nit): `lock`/`unlock` on a barrier without a `key_item` says "You don't have the key."**
See `kernel/ts/play/text.ts:215-216`. Failure: in `ashmere_gate`, `lock n` on the oak door (no
key_item) prints "You don't have the key." That suggests a key exists somewhere. The code
`not_owned` is right. The words could say "It has no lock." when the barrier has no key_item.
This is presentation only.

**Q1 (question): the door commands require `direction`
(`protocol/command.schema.json`).** 00 §4.1 has an R5 row "Containers with locks and capacity
(Barrier + capacity)". A barrier on a chest cannot be named by a direction. Is that row a later
slice, and will it add an optional `target_id` (additive for old commands) rather than a second
command family? Nothing in this PR is wrong; the question is only which way the frozen command
grows.

**Q2 (question): the GameView exposes a barrier only as an exit's unavailability reason.** An
open door's exit looks like a doorless one, so a touch client cannot offer `close` (or `lock`
on an open door). The brief puts GameView changes beyond availability out of scope; I assume the
GameView-for-touch slice picks this up.

Over-engineering: nothing to cut. `byRef` replaced `specs` rather than adding a twin, and
`Loka.Content.Barriers` exists for credo and the size limit. `reason` moved to `text.ts` without
changing its content (the moved table is identical plus the barrier rows). Emergence: the
composes-with statement holds. `movement` names barrier state through `passage`, which 21 §5
Connection ("barrier state") and the S6b lesson require. No capability code names content.
