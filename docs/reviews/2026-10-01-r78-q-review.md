## Requirements derived before reading the diff

1. A cartridge declares an offered quest with one objective. The objective declares its evidence policy (06 §43).
2. `accept_quest` (registry name) creates one active player-scope instance through `quest.activate` and emits `quest_activated`. A second activation and an undeclared quest are refused, never faulted.
3. A current-state objective is evaluated on the state at hand, never latched. A lantern held before acceptance gives credit (`activated_with_possession`, adverse `early-possession`). One no longer held gives no credit.
4. A strict objective counts only acquisitions after activation, by the instance's actor (06 §5, 04 §5.2 step 5). An earlier acquisition never counts.
5. Resolution goes only from an open instance through legal transitions (06 §1). It re-checks a current-state objective now. The frozen traces keep `quest: active` until the choice resolves it.
6. `quest_state` needs both halves, the rule in world.ts and the leaf in `holds()`. Unknown quest references fail at load (04 §5.3: "Unknown ... policies ... fail validation").
7. Both kernels' cartridge checks stay in step.
8. No frozen fixture or registry entry changes.

## Diff against the list

1 to 8 are met. No frozen conformance or protocol fixture is modified; `invalid.json` and the new known answer are append-only. The registry is unchanged.

## Findings

**B1 blocker**: `kernel/ts/src/quest.ts:64`. The `q.state === 'active'` filter in `deliver` has no test; mutant M3 leaves the whole TS suite green.

- Failure if it regresses: a strict quest goes accept, take (`objectives_complete`), drop, take.
- The second take faults `precondition_failed` on the quest target. `deliver` emits `from: active` for a non-active instance, and the whole proposal is discarded.
- Every later take after the quest resolves faults the same way. The player can never pick the item up again.
- Verified by probe.
- Fix: one test row in which re-taking after `objectives_complete`, and after `resolved`, is accepted and leaves the state unchanged.

**S1 should-fix**: `kernel/ts/src/cartridge_quests.ts:17` and `lib/loka/content/quests.ex:30`. A quest key equal to a recipe key or an action key is DUPLICATE_DEFINITION in both kernels, but no test pins it. Removing `recipe` from the taken set survives both suites (E4 and its TS twin).

- Failure: a cartridge whose quest key equals a recipe key loads.
- `actions.ts cartridge()` then spreads the offer last into `Object.fromEntries`, so the recipe silently disappears from the ActionSet.
- Fix: one row per kernel.

**S2 should-fix**: `lib/loka/content/recipes.ex:164`. A room contribution may name a quest offer, but nothing tests this in Elixir (E5 survives).

- TS tests it (`quests.test.ts` `contributed`).
- Failure if it regresses: the compiler rejects UNRESOLVED_REFERENCE a cartridge the loader accepts. The two kernels drift unseen.
- Fix: one Elixir row.

**S3 should-fix**: `kernel/ts/src/actions.ts:176`. An accept of an undeclared quest is `unsupported_capability`, while `perform` of an undeclared recipe is `not_found`.

- error_registry.json defines `not_found` as "The referenced thing does not exist".
- Failure: a client gets "capability not supported" for a typo'd or stale quest ref on a cartridge that does lock quest@1.
- A second accept staying `unsupported_capability` (the offer is withdrawn) is fine.

**N1 nit**: `protocol/quest.schema.json:68`. The description says strict objectives stop at `objectives_complete` and cites "the Tiny fixture". The frozen Tiny `cases.json` shows `resolved` right after the strict take, which is automatic resolution. Cite Tiny only for "an acquisition before activation never counts".

**N2 nit**: `kernel/ts/test/quests.test.ts`. Instance ids are read back from the output (`op.instance_id`, `Object.keys(done.state.quests!)[0]`) rather than written as IdSource literals. The asserted from, to and writer_group fields are literal, so the risk is low.

## The developer's open questions

1. **Active until resolved, then active → objectives_complete → resolved in one group:** agree. This matches lantern-traces (`quest: active` through `talk`) and 04 §5.3 (successive legal transitions in one explicit sequence compose).
2. **Unmet objective is `quest_requirement`; slice D checks custody first:** agree, carried to D. D must check custody and Bram's presence before calling `resolution`, for both outcomes. `carry` has no transfer, so nothing else enforces custody. A strict quest at `objectives_complete` after a drop is not re-checked by `resolution` either. Frozen answer: `not_owned` (adverse `drop-after-choice-opened`).
3. **Undeclared quest is `unsupported_capability`, not `not_found`:** they should match; see S3.
4. **Lock through the `quest_activated` event:** agree. This follows the check@1 precedent (a recipe's check is locked by its events). A registry `definitions` entry would trip the brief's registry scope trigger.
5. **No automatic resolution:** acceptable for Q. The Lantern resolves by choice, and the schema states that further fields join as optional fields (cartridge.schema precedent: an optional map, the tag stays). Automatic resolution, which the Tiny fixture uses, is a later additive field. See N1 for the wording.

## Other checks

- **Over-engineering:** none to cut. `row` moved to decision.ts with a re-export for the mobile store. That is acceptable.
- **Composes-with:** accurate. `deliver` reads `item_acquired`, a shared DomainEvent. 06 §5 requires that quests consume events, and the schema closes the objective to that one type. `accepts` names `accept_quest`, as it already names `perform`. Writes are only `quest.*` ops.
- **Carry to D:** both `deliver` and a resolving rule allocate writer groups. If one decision both acquires and resolves the same instance, `deliver`'s `active → objectives_complete` conflicts with the resolution sequence. The ponytail note in quest.ts covers the activation half only.
