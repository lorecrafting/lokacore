## Findings

1. **blocker** (twin composition contract: both kernels must return equal results for every `composition.json` delta, and this slice's new final check breaks that), `kernel/ts/src/foundation/compose.ts:75-78` vs `lib/loka/core/compose_job.ex:21` (`unrun`) and `lib/loka/core/compose.ex:39-44` (`finish`). TS returns the first unrun job in overlay insertion order. Elixir `Enum.find_value` walks the map in sorted key order. Run: fixture `job-schedule-inside-advance-never-run` with a second schedule `d9000000-…` (due 40) placed before `d2000000-…`. TS faults `nonfuture_job` on job d9 and Elixir faults on job d2 (both run in a scratch worktree, then removed). By reading only (not run): with a choice at its limit and an unrun job in one delta, TS returns whichever comes first in overlay order, and Elixir always returns `precondition_failed`. The host proposal never emits such a delta. Fix: one deterministic order in both kernels, plus one fixture case.
2. **nit**, `kernel/ts/src/runtime/proposal.ts:267`. `populationDeadlinePairs` is computed once, before the drain. A drain reaction (or FD1's `runDelayed` after the batch merge) that starts a suppress plan whose `ends_at` equals a plan job's due time inside the wait leaves the pair ungrouped, so one wait faults `conflicting_write` where steps pass. No shipped content does this: `d9_suppress_hounds` is set by a player action. Follow-up filed: loka-7n60.
3. **nit**, `kernel/ts/play/main.ts:96-100`. The play CLI's `wait N` sends one advance and does not go through `elapsed.ts` boundary. `wait 72` through a fight of more than about 64 rounds faults `budget_exceeded`. Before this slice it faulted `nonfuture_job`, so this is not a regression. The known limit in protocol.md names only the host.
