- **Developer question (RNG parity rests on the dusk row): acceptable for R6P P6b; carry on row 5.** Row 11's

## Findings

- **F-1 should-fix** — docs/evidence/2026-10-02-r6p-iphone11/README.md:60-64. The owner-save claim ("hashed
  `1710b653…` and `fb0b9878…` before and after, equal to the pre-install copy") exists only as truncated
  prose; no shasum output is in the hashed bundle. Failure scenario: had a harness or UI build overwritten
  `loka-lantern.db`, the record would read the same, so a reviewer cannot tell an untouched save from a
  reported one. Fix: retain the full `shasum -a 256` lines (names only, no paths) for the pre-install copy
  and the copies before and after the final reinstall as a file in the folder, listed in SHA256SUMS.
- **F-2 should-fix (fix in the owner-row run)** — dev-harness.ts.txt:509-510; README.md:40. "Cold restore"
  is never measured cold: `restore` runs after `open_new` in the same process (the README says so). The
  envelope §4 asks for cold load and restore apart from warm; the true cold reopens of a played save
  (`carry2`, `leave2`, `hold*b`) are untimed. Failure scenario: a relaunch restore that is slow only on
  first open (schema check, statement prep) is never seen. Fix: time the first open of a played save in a
  fresh process (swap the order, or time `carry2`'s open) in the rebuild for rows 13/14.
- **N-1 nit** — dev-App.tsx.txt:36-41. `read` and `write` lack the `p6-` guard that `open` and `remove` have.
  Scenario: the harness is reused for rows 13/14 and an edit passes a non-p6 name to `write`, overwriting an
  owner save. One line each.
