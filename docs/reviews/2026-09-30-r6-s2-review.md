## Requirements derived from the spec (written before reading the diff)

Sources: ROADMAP S2, 03 §§14-15, 15 OFF-03 to OFF-06, ADR-072, ADR-075 §4 and line 37 (phone placement and cap "decided by R6"), and the S1 review.

1. A failed COMMIT is not proof of rollback. While the outcome is unknown, no decision or replay runs from memory; every entry point is fenced, and the reply is a retryable transient ("commit pending", 03 §14), never saved success.
2. Reconcile reads only the authoritative store, and only once no transaction is open on the connection. A receipt present: adopt the stored state and return the stored outcome, with no second decision or RNG draw. Confirmed absent: memory stays at the prior revision, and a retry of the same identity is a fresh attempt.
3. A restart after commit-before-memory or commit-before-reply loads the committed state once (OFF-04, OFF-05). A definite write failure is a recoverable error, and memory and storage stay put (OFF-06).
4. The trace is derived. It is written after the commit, one entry per command, and failed commits are included. An unknown commit gets exactly one follow-up entry at the same ordinal; a retry takes the next ordinal. Every entry shares the header's `run_id`, `content_hash`, `kernel_version` and `seed`. A trace failure never changes the game, the receipt or the reply. An entry survives commit-before-trace interruption.
5. Shipped code uses only expo-sqlite's sync API and Hermes-safe code, on one connection. Faults are real where they can be, and simulated ones are labeled as simulated.

Items 1-3 and 5 are met. Item 4 fails twice (S-1, S-2).

## Findings

**S-1 should-fix: a trace read error reaches the game and can stop the save from opening.** Locations: `trace.ts:66`, called from `authority.ts:147` and `authority.ts:34`.
- `recover()` runs `getAllSync` outside any try. `traceCommand` swallows its own errors; `recover` does not.
- Probe, first action: rename `trace` so a committed take's trace write fails and `behind` becomes true.
- Probe, second action: the give commits (head revision 2), then `invoke` throws `no such table: trace`. A committed save is reported to the player as an error.
- In `openStory` the same throw aborts the open. A derived store then blocks the authoritative one, which ADR-075 §4 "derived, never authority" forbids.
- Fix: one guard inside `recover` that returns false on error, so both callers are covered.

**S-2 should-fix: entries written in a later process carry that process's ids, not the header's.** Location: `trace.ts:39-51`.
- The header is written once, when the table is empty. Each entry takes `ids` from the current `openStory` call.
- Probe: process 1 takes the satchel, then process 2 gives it with a different `kernel_version` and `run_id`. The rows come out as header `k/6f6f`, entry `k/6f6f`, entry `k2/7f7f`.
- This breaks ADR-075 §4's rule that every entry shares the header's ids. `recover()` also records an entry decided by the old kernel under the new `kernel_version`, so a replay "under the recorded `kernel_version`" uses the wrong kernel.
- An app update (a new `kernel_version`) or a content update (`content_hash`, S3) triggers it.
- The suite passes one constant `ids`, so it cannot catch this.
- Fix: detect a mismatch and handle it, for example with a new run header, or record a bounded owner for it.

**S-3 should-fix: the trace placement decision exists only in the PR body.**
- ADR-075 line 37 leaves phone placement and the size cap to R6.
- Failure scenario: S3's garbage collection or S6's "retain failing traces" does not know the trace lives in the save DB and shares its lifetime and backup.
- Fix: record placement, meaning the `trace` table in the save DB on the one connection, in ROADMAP S2 or an ADR-075 note (S2 owns this). Name the slice that sets the cap; S6 is suggested.

**Nits**
- N-1 `trace.ts:67,70`: no test covers the `command != 'null'` filter. `every()` also stops at the first failed write, so a single receipt that cannot be traced blocks every later recovery.
- N-2 `authority.ts:146-148`: if the trace is behind when an unknown-then-committed settle happens, `recover` writes only the `committed` entry, and the `unknown` entry is lost.
- N-3 `store.ts:51-54`: `load()` does not check `isInTransactionSync()`. If the first save's COMMIT and both ROLLBACKs fail, reopening on the same handle reads the uncommitted head as saved. The world is identical to `fresh`, so the harm is low.
- N-4 `authority.ts:146-150`: if `recover` fails twice in a row, a fault or failed entry can take an ordinal ahead of an earlier committed command, so replaying by ordinal decides it against the wrong world.

**Question**
- `world()` (`authority.ts:35`) is not fenced and serves the prior revision while `pending`. 03 §15 fences only decisions, and every decision or replay passes through `invoke`, which settles first. Is the stale view acceptable to the UI slice?
