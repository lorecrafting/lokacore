## Must be true (written before the diff)

1. Without `--lan`: one plain-http listener on 127.0.0.1:19006, as before. With `--lan`, loopback stays plain http, and https binds only the LAN addresses.
2. The CA lives in `~/.loka/lan-ca`: dir 700, keys 600. It is made once and reused. Its key is never in the repo, a log, the terminal or any response.
3. The CA has basicConstraints critical CA:TRUE, keyUsage keyCertSign/cRLSign, and critical nameConstraints permitting only 10/8, 172.16/12 and 192.168/16 (plus `.local`). A leaf for a public IP or name must fail verification.

5. The CA download serves only the certificate, only with its token, and stops when the pairing expires.
6. Pairing is as in #781, except the cookie gets `Secure`. The author server takes only the paired `https://` Origin.
7. The docs give plain iOS and Android steps and replace "cannot save yet".

## Findings

### Blocker 1: the 172 name constraint has no red control

`mobile/app/lan.cjs:22`, `mobile/app/lan.test.ts:110-113`.
- Both 172 mask mutants pass the suite.
- `/240.0.0.0` permits 160/4, so a leaked key could again vouch for public hosts (172.217.x is Google).
- `/255.255.0.0` breaks a phone on a 172.20.x network, which `lanAddresses` still serves.
- The test checks only 8.8.8.8 and `example.com` failing.
- Fix: add boundary leaves to the test.
  - These must pass: 172.16.0.1, 172.31.255.1, 192.168.255.1.
  - These must fail: 11.0.0.1, 172.32.0.1, 192.169.0.1.
- Show the new asserts going red on both mutants. The PR body's claim "Red: nameConstraints entries" is backed only for the DNS entry.

### Should-fix 1: the phone steps skip the fingerprint check

`docs/guides/writing-the-game.md:60-65`.
- The CA travels over plain http. The terminal says to check its SHA-256, but the doc goes straight to full trust.
- Failure scenario: a spoofing device on the Wi-Fi answers on port 19005 with its own root, which has no name constraints. The owner follows the doc and turns on full trust, and every https site on the phone can now be intercepted.
- Fix: before Install (iOS: More Details; Android: the certificate details), compare the SHA-256 with the terminal's. Restore #781's "use it only on a network you trust".

3. `lan.cjs:39`: the docstring says "the key stays in memory", but `leaf.key` is written to disk (line 70).

### Questions (for the owner's deferred phone check)

- Android 11+: Chrome may hand `application/x-x509-ca-cert` to the system installer, which refuses with "install in Settings" and may leave no file to pick. Does the file land in Downloads?
- The browser proof trusted the leaf's SPKI. A browser trusting only the CA (so the name constraints get evaluated) is still unproven on iOS. Apple's `verify-cert` above passes, which suggests it will.
