## Requirements derived before reading the diff

1. A save opens on the installed release whose exact hash it pins (10 §16 "A save references
   exact hash"; 10 §32; OFF-11), not on the newest one; its trace uses the pinned hash.
2. New saves and new games pin the newest bundled release (10 §32 "New runs normally use the
   latest approved release").
3. A pinned release that is not installed gives `pinned_release_missing`; nothing is written,
   no head adopted (10 §32 "Missing required package: preserve the current working state").
4. An unknown or newer save format (07 §9 "save format version") gives
   `unsupported_save_format`, checked before any row of the save is read as world state or any
   table is created; nothing is written.
5. Neither refusal may lead to losing the only save the player has when the fix is outside the
   save (10 §31 "Never discard the only working/unbacked save"; 10 §32 "preserve the current
   working state"); a new game, where offered, replaces only after confirmation (10 §31
   amendment) and keeps pending milestone reports (23 §11).
6. Carried, not findings: GC, migration staging, recovery copy, downloads, pending restores;
   OFF-12 as a release-process obligation.

## Findings

**S3B-1 — blocker — `mobile/authority/local-story/authority.ts:64-67`
(also `:48`, `store.ts:117-118`, `saves.test.ts:219-238`, `docs/ROADMAP.md:65`).**
`refuse` attaches `newGame` to `unsupported_save_format`. I agree with the PM ruling: a save of
a format this app cannot read is recovered by updating the app, not by a new game, so the typed
result must not offer one. Failure scenarios: (a) a save written by a newer app (restored backup
or app downgrade) whose tables this app's `replace` happens to accept: the UI offers "new game",
the player confirms, and the only save is replaced by an app that cannot even read it
(`saves.test.ts:238` asserts exactly this succeeds); (b) a newer format with a differing table
(`saves.test.ts:226`, renamed `pin`): the offered `newGame` throws on every attempt
(`store.ts:117` documents it), an action that can never succeed. Pending milestone reports
survive `replace` today only because it never touches `report`, while a newer format's report
shape is unknown to this app (23 §11). Fix: no `newGame` on `unsupported_save_format`; the test
asserts its absence for both shapes and drops the `startOver` there; the `store.ts:117` ponytail
comment goes with it; reword `authority.ts:47-50` and the ROADMAP S3b acceptance ("offer only a
new game") so only `pinned_release_missing` and `save_corrupt` offer one.

**S3B-2 — question — `mobile/authority/local-story/authority.ts:65-71`.**
The format is read from `save.format`. A future format that renames or drops the `save` table
is not detectable: it falls to `load`, which runs `SCHEMA` (creating tables) and reports
`save_corrupt` with a new game offered. Is "every future format keeps `save.format`" a
release-process obligation worth one line in the decision record beside OFF-12?

which is S3B-1(b) again on the corrupt path. Fix: either the new game recreates the `save` table
inside its transaction, or this case is carried to S6 beside the existing NOTADB item. Either
way, the test calls `newGame` and checks the result for each case it says moves on.
