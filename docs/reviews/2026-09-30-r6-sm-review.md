## Findings

**S-1 should-fix, `mobile/authority/local-story/smoke.ts:66`.** The next id is `count(*) FROM receipt`. Replies without a receipt (`invalid`, `fault`, `conflict`, and S2's `pending`) still use up an id. Probe run: an invalid invocation, then `take`, then a restart; the first press after the restart answered `(conflict)`. If the colliding receipt has the same intent, the press instead replays silently and shows the old outcome, but nothing changes. SM2 reuses this controller. Fix: resume from `max(invocation_id)`. The hex ids are zero-padded, so they sort correctly as text.

**S-2 should-fix (merge order with PR #69), `smoke.ts:64` and `smoke.test.ts:18-23`.** The two PRs touch no common file, so git reports no conflict, but they break each other. #69 changes `openStory(db, fresh, scope)` to `openStory(db, fresh, scope, ids: RunIds)` and adds `isInTransactionSync` to `Db`. Whichever PR merges second must first rebase onto the other. It must pass `ids` at `smoke.ts:64`, which tsc will flag. It must also add `isInTransactionSync: () => sql.isTransaction` to the test adapter, which tsc will not flag because `tsconfig.json` excludes `*.test.ts`.

**N-1 nit, `docs/ROADMAP.md:50,70`.** The R6 count "6 + 1" and "31 planned slices … 7 R6" do not include SM.

**N-2 nit, `mobile/app/App.tsx:10`.** A Fast Refresh edit of `App.tsx` runs the module again and opens a second handle, the double-open the mobile lessons warn about. This happens in dev only. Strict mode and remounts are safe, because the handle is opened at module level.

**Q-1, white screen on a cartridge load failure (`smoke.ts:62`).** This is acceptable for a smoke screen. `smoke.test.ts` runs the same fixture through the same loader, so a failure on the phone would come from Hermes only. In dev, the red box shows the message.
