## Findings

**S-1 should-fix, `mobile/authority/local-story/smoke.ts:66`.** The next id is `count(*) FROM receipt`. Replies without a receipt (`invalid`, `fault`, `conflict`, and S2's `pending`) still use up an id. Probe run: an invalid invocation, then `take`, then a restart; the first press after the restart answered `(conflict)`. If the colliding receipt has the same intent, the press instead replays silently and shows the old outcome, but nothing changes. SM2 reuses this controller. Fix: resume from `max(invocation_id)`. The hex ids are zero-padded, so they sort correctly as text.

**S-2 should-fix (merge order with PR #69), `smoke.ts:64` and `smoke.test.ts:18-23`.** The two PRs touch no common file, so git reports no conflict, but they break each other. #69 changes `openStory(db, fresh, scope)` to `openStory(db, fresh, scope, ids: RunIds)` and adds `isInTransactionSync` to `Db`. Whichever PR merges second must first rebase onto the other. It must pass `ids` at `smoke.ts:64`, which tsc will flag. It must also add `isInTransactionSync: () => sql.isTransaction` to the test adapter, which tsc will not flag because `tsconfig.json` excludes `*.test.ts`.

**N-1 nit, `docs/ROADMAP.md:50,70`.** The R6 count "6 + 1" and "31 planned slices … 7 R6" do not include SM.

**N-2 nit, `mobile/app/App.tsx:10`.** A Fast Refresh edit of `App.tsx` runs the module again and opens a second handle, the double-open the mobile lessons warn about. This happens in dev only. Strict mode and remounts are safe, because the handle is opened at module level.

**Q-1, white screen on a cartridge load failure (`smoke.ts:62`).** This is acceptable for a smoke screen. `smoke.test.ts` runs the same fixture through the same loader, so a failure on the phone would come from Hermes only. In dev, the red box shows the message.

## Fix round 2: `caa2f3d` (answers Astra round 1)

Verdict: **APPROVE** (one nit). The six smoke tests pass.

- **SM-1, resolved (`smoke.ts:114`, `:126`).** The unconfirmed invocation is kept and resent unchanged, with the same id and intent, until a reply other than `pending` clears it. Mutants:
  - a new id on every press: 2 tests fail;
  - always clearing the retry: 3 fail;
  - never clearing it: 3 fail.
- **Pending never sticks after a not-committed settle.** The fenced attempt has no receipt, so `invoke` decides the same id afresh and the retry clears.
- **N-4 nit, `smoke.ts:114-126`.** A definite failure, or a settle that confirms no commit, makes `invoke` throw. Because `retry ??=` was assigned before the call, it survives the throw, so the screen shows "Save not confirmed (pending)", and the next button resends the failed action instead of the one pressed. Probe: "Go north" fails on its receipt insert and throws; pending is true; pressing "scan" logs `> Go north`, `moved`; pending then clears. This is not a false success, and resending an id that has no receipt is correct under 03 §14, but "pending" is the wrong label. In Release, the throw from `onPress` is probably fatal anyway. Fix (optional): clear `retry` in a `catch` before rethrowing.
- **Pending is memory-only.** It lives in the `openSmoke` closure, and a restart drops it. After a restart, `lastId` either counts the id (if it committed) or reuses it (if it did not), so nothing collides.
- **SM-2, resolved (`smoke.ts:80`).** The allocator reads only ids with the `00000000-0000-4000-8000-` prefix. Removing the `LIKE` filter fails the new test. The read-only SELECT outside `openStory` carries a `ponytail:` comment, which I accept.
- **SM-3, resolved (`App.tsx:12`).** `globalThis.loka_smoke ??=` reuses the controller across Fast Refresh, and nothing closes the handle, so the guard cannot hold a closed one. Holding a reference on `globalThis` also stops the handle from being garbage-collected. A full reload creates a new JS context, the same as a cold start.
- **SM-4 and SM-5 deferred by the PM.** Both have `ponytail:` comments (`smoke.ts:26-28`). ROADMAP R6 SM now requires `kernel_version` from the build before any phone trace counts as evidence (this covers my N-3), and the S3 row allocates lineage and run identity per save and per fork. The deferral is consistent with the "not gate evidence" scope.
