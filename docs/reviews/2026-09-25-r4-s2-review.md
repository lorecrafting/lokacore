# Review: R4 S2 — Elixir cartridge compiler (R4 minimal)

PR #27 (`r4-s2-compiler`), commit reviewed `cd27deaa9081854aa0207e229c5a676edb605697`.
Reviewer: independent (Fable; authored none of the work). Full review: the slice produces
the bytes the cartridge hash covers. CI green on the head (elixir, typescript, lint, android,
ios); baseline in a fresh detached worktree: 141 passed.

## Verdict: CHANGES REQUIRED

Three should-fixes, each small. The hash, the known answer, determinism, the path grammar,
the diagnostic order, the capability checks and the boundary change are sound. Two rejected
files cascade into false second causes (the PR's own 08 §6 argument), and one plausible
break of duplicate-key detection leaves the suite green.

## Must be true (written from the spec before the diff)

1. Same source twice gives identical bytes; authored key order (maps over 32 keys) and
   file listing order never reach the output (14 Gate R4; CAR-04; C3; contracts lesson).
2. `content_hash` is SHA-256 of the canonical bytes of `cartridge` only; the artifact is
   `{"cartridge":…,"content_hash":"…"}` canonical; the hello subset reproduces
   `protocol/fixtures/cartridge_hash.json` (05 §11, §20; the Python oracle).
3. Definition maps are keyed `id@version:kind/key` with the key inserted (05 §4; C1);
   the lock is exactly `requires.capabilities` (C4).
4. Diagnostics are the frozen shape; `message_key` is `diagnostics.<lowercase code>`; the
   path follows the grammar (source without `.json`, literal when a segment is not
   `[a-z0-9_]+`; `.name`, `["…"]`, `[n]`); order is path, code (UTF-8 bytes), canonical
   encoding; identical diagnostics appear once (08 §6; CAR-02; Diagnostic description).
5. Duplicate JSON keys are rejected at any nesting level, never first-wins.
6. Dotted fact names map `.` to `_`; two names mapping to one key fail; 64 applies after
   mapping as SCHEMA_VIOLATION (IMPORT.md owner decision).
7. Unknown field, capability (at that version), command, policy-op owner not required,
   broken reference, wrong fact_compare type, empty or reversed kernel range, pin other
   than 1, server_only under offline_private all fail (05 §3, §5, §6; 06 §21; A10; C4).
8. Every emitted code is reachable, and asserted as a full literal not derived from the
   compiler; the code set is the schema's, with NESTING_TOO_DEEP as a PM-approved addition.
9. An artifact over the cap is ARTIFACT_TOO_LARGE and never written.
10. Diagnostics are complete across files and do not cascade (08 §6 repair loops).
11. `Loka.Content` depends only on `Loka.Core` (02 §1); Core exports only what Content uses.
12. Tests follow AGENTS.md "Writing tests"; source files under 300 lines, total near the
    brief's ~530.

## Checked

- **Known answer.** `@hello_artifact` is built from the fixture's `canonical` and `sha256`
  fields with the framing hand-derived (`"cartridge"` sorts before `"content_hash"`); the
  compiler never supplies an expected value. `cartridges/ashmere_hello` is the 00a §12
  subset in authored key order. Item 2 holds.
- **Determinism.** Outputs are maps keyed by DefinitionRefString, encoded by
  `Loka.Core.Canonical` (sorted ASCII keys); the diagnostic sort key is
  `{path, code, canonical}` and Elixir compares binaries bytewise, so the order is total
  and byte-ordered. The 40-key facts map and reversed manifest test exercise the sort past
  the 32-key small-map boundary. Item 1 holds.
- **Path grammar** (`Source.at/2`): segments checked against `[a-z0-9_]+`, `.json` suffix
  required, otherwise the whole relative path as a canonical literal; members `.name` or
  `["…"]`; JSON-pointer segments become `[n]` exactly where the value there is a list.
  Verified on `.hidden/x.json`, `policies/Bad Name.json`, `facts.facts["a.b"]`,
  `actions/talk.input[0]`, `policies/p.root.items[3].fact`. Item 4 holds.
- **Encode cannot fail after checks.** Probed: an integer above 2^53 in `version`,
  `priority`, an int default and an int bound is `SCHEMA_VIOLATION invalid_type`; invalid
  UTF-8 and a lone surrogate escape are `INVALID_JSON`; every map key in the frozen shapes
  is pattern-bound or `additionalProperties: false`; depth is NESTING_TOO_DEEP (123 nots
  compile and pass `Canonical.decode`, 124 fail). The `{:ok, bytes} = Canonical.encode`
  match in `Loka.Content.compile/2` is safe.
- **Boundary.** `Loka.Core exports: [Canonical, Contracts]` is the two modules Content
  calls, not the whole boundary; Content → Core is the 02 §1 direction; the mix task is
  `top_level?: true` with `deps: [Loka.Content, Mix]`. `Canonical.max_depth/0` replaces a
  duplicated 128. Item 11 holds.
- **Mix task.** Writes `compile/2`'s bytes unchanged; on error prints one JSON line per
  diagnostic to stderr, exits `{:shutdown, 1}`, writes nothing (tested).
- **Sizes.** 65 + 168 + 161 + 145 + 23 = 562 source lines; largest file 168; test 426.
- **Tests.** Expected values are literals or the KAT; `errors/2` validates every
  diagnostic against the Diagnostic contract; real files in `tmp_dir`; no mocks; each test
  names its break.
- **Mutants** (`mix test --force test/loka/content_test.exs`, tree restored after each):
  - sort key `{code, path}` → 1 failure (order test);
  - hash over `bytes <> " "` → 3 failures (KAT, cap, mix task);
  - reference version unchecked → 1 failure;
  - `@enclosing 2` → 1 failure;
  - `duplicates/2` list clause disabled (arrays not walked) → **24 passed** (F3);
  - `Enum.uniq()` removed → 24 passed (note below, not a finding).
- **Probes** (`Loka.Content.compile/2` on edited copies of the hello source):
  `cartridge.json` = `{` and `cartridge.json` with a repeated key (F1); `facts.json` with
  invalid UTF-8, a repeated key, an extra top-level field, and absent (F2); a repeated key

## Findings

### F1 (should-fix) — a rejected `cartridge.json` also reports MISSING_MANIFEST

`lib/loka/content/compiler.ex:32` (`manifest([], _)` emits MISSING_MANIFEST whenever no
decoded manifest reaches it); `lib/loka/content/source.ex:16` (files that fail to decode
are left out, indistinguishable from absent).

Failure scenario: `cartridge.json` is `{` (or repeats `id`). Output: `INVALID_JSON` at
`cartridge` **and** `MISSING_MANIFEST` at `cartridge` (observed). The schema defines
MISSING_MANIFEST as "the cartridge has no cartridge.json"; here it has one. A repair loop
reading codes (08 §6) is told to create a manifest that exists. The PR body rejects exactly
this kind of "false second cause" for references; the same rule applies here.

Fix: distinguish "present but rejected" from "absent" (for example `Source.load/1` returns
`{rel, kind, :invalid}` for a rejected file, and `manifest/2` maps it to `{nil, []}`).

### F2 (should-fix) — a rejected `facts.json` makes every fact reference UNRESOLVED_REFERENCE

`lib/loka/content/compiler.ex:64-73` (`facts/1` returns `{%{}, diags}` when the file fails
its file-level schema; a load failure never reaches it, so the map is `%{}` too);
`lib/loka/content/checks.ex:148` (`target == nil` → UNRESOLVED_REFERENCE).

Failure scenario: the hello source with `facts.json` containing invalid UTF-8, or a
repeated key, or an extra top-level field (`"api_version": "loka/v3"`, which the 00a §12
`facts.yaml` has). Output: the true diagnostic at `facts…` **plus**
`UNRESOLVED_REFERENCE` at `policies/village_arrived.root.fact` with
`target ashmere_hello@0.0.1:fact/village_arrived` (observed for all three). The fact is
declared; the reference is fine. The PR's ruling "references to invalid definitions
resolve" is applied per definition but not when the whole facts file is rejected, which is
the more common authoring error (a stray field, a bad edit). A missing `facts.json` with
a fact reference is correctly UNRESOLVED_REFERENCE (the fact really does not exist).

Fix: when `facts.json` is present but rejected at load or file level, treat the fact
namespace as unknown and skip fact-reference resolution (the same shape as `check/3`
skipping `uses/3` when the manifest is nil, `checks.ex:60`). Add one test with a literal
expected list for each of F1 and F2.

### F3 (should-fix) — duplicate keys inside array elements are unguarded by the tests

`test/loka/content_test.exs:129-136` (the only DUPLICATE_KEY case is `target.kind`, an
object inside an object); `lib/loka/content/source.ex:66` (the list clause of
`duplicates/2`).

Failure scenario: the list clause is dropped or reordered in a later edit.
`policies/p.json` with `{"op":"target_present","op":"x"}` inside `root.items[0]` decodes
first-wins and compiles silently; `mix test --force` stays green (verified: 24 passed with
that clause disabled). The brief's focus item is "duplicate JSON keys truly rejected at
every nesting level"; the code does it (probe verified), the suite does not hold it. One
added assertion in the DUPLICATE_KEY test (a repeated key inside `policy.root.items[0]`,
expected path `actions/talk.policy.root.items[0].op`) closes it.

### N1 (nit) — a missing source directory reports MISSING_MANIFEST

`lib/mix/tasks/loka.compile.ex:11`, `lib/loka/content/source.ex:24-31`. `mix loka.compile
typo/ out.json` (or a path to a plain file) prints `MISSING_MANIFEST` at `cartridge` and
exits 1. True in a sense, misleading in practice; S3's end-to-end test will pass a path.
`File.dir?/1` in the task with a usage error is one line. Not a spec requirement.

## Notes (no action required)

- `Enum.uniq()` in `Loka.Content.sorted/1` cannot be reached by any R4 source: `finish/2`
  reports each repeated key once, collision groups have distinct names, and `body/4` drops
  the validator's `/key` error that would duplicate `authored_key/3`'s. Keep it: the
  contract says an identical diagnostic appears once, and it is one call.
- FACT_NAME_COLLISION is reported on names that are also pattern-invalid (`A.b`, `A_b`
  in the order test). Both causes are real; accepted.
- `has_item` and `quest_state` references are always UNRESOLVED_REFERENCE in R4 (no
  frozen items or quests). Correct under A10; S3 and R5+ fixtures should not expect otherwise.
- PM rulings challenged: none. Full DefinitionRef objects in source, DUPLICATE_DEFINITION
  unreachable, UNDECLARED_CAPABILITY for commands and ops only, `data {}` where the schema
  defines none, NESTING_TOO_DEEP (path at the definition, `{maximum}` from
  `Canonical.max_depth/0`), the registry option, ARTIFACT_TOO_LARGE at `""`, and the
  `ponytail:` non-UTF-8 limit are all consistent with the schema and the brief.
- Over-engineering: nothing to cut. `pointer_steps/2` is needed (the grammar distinguishes
  `[n]` from `.n`); the glob escape is needed (tested); `Source.diag/4`'s `suggested`
  default is used once, by UNDECLARED_CAPABILITY.
