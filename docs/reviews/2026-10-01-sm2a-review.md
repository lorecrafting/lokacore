## What must be true (written before reading the diff)

Sources: 15 OFF-07; 03 §§14-15; 10 §§31-32 as amended; ROADMAP SM2 row; the brief; `docs/lessons/storage.md`, `docs/lessons/mobile.md`.

1. No path deletes or replaces a save without the player's confirmation. A file is deleted only when SQLite reports it corrupt. A healthy save, or one whose open failed for a transient reason, is never deleted (10 §31: never discard the only working save).
2. A newer app's save is never destroyed (10 §32; the S3b blocker).

6. No throw escapes `press`. Corruption found during play is shown with Start over.
7. Start over gives a playable fresh game at the entry room under a new run with no parent (10 §31).
8. The decision record matches the brief text and is marked (paraphrased). The SM2 row has 3 slices and the count is +2.

## Findings

No blocker, no should-fix.

- **N1 nit** `mobile/authority/local-story/smoke.ts:199`: no test covers `replace: true` after a failed `remove()`. Mutant: dropping it leaves the player with no Start over button until a restart (for example, `deleteDatabaseSync` throws once). After a restart the file re-enters the corrupt path, so the player is not stuck for good.
- **N2 nit** `mobile/app/App.tsx:15-16`: the `ponytail:` comment says a hot `-journal` "would be rolled into the fresh file". SQLite deletes a journal that sits beside an empty database file instead of replaying it, so the comment overstates the risk and could prompt an unneeded `expo-file-system` dependency.
- **N3 nit** `mobile/app/App.tsx:52`: `s.failed` is cleared only on reopen. Scenario: Start over fails (read-only), a press succeeds, and a later press faults (disk full). The screen then shows "Start over failed: readonly" although no Start over was attempted.
- **N4 nit** `mobile/app/SaveError.tsx:23` with `smoke.ts:188`: a pending Start over during play on a healthy save (an earlier press's COMMIT unknown) sets no `kind`. The screen then says "The save could not be opened.", which is false; the message should say the start over is not yet confirmed.
- **N5 nit** `mobile/authority/local-story/smoke.ts:175`: `!kind &&` is dead code. A refusal's error message is its kind, which never matches `corrupt()`, so the mutant is equivalent.
- **Q1 question** (R12): `newGame` does not touch `report`. A corrupt `report` page that play writes to (a milestone cartridge) would fault, and Start over would "succeed" in place each time, a loop. The items cartridge writes no report, so it cannot happen today. Should it be named among the R12 typed-detection carries?
