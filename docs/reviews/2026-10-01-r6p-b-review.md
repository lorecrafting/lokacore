## Findings

**B-1 (blocker): a refused or rejected command never becomes `budget_exceeded`.** At `kernel/ts/src/world.ts:103-105` a refusal returns before any count is compared. At `kernel/ts/src/proposal.ts:51`, via `propose`'s `root.kind !== 'accepted'` return, a rule rejection does the same. `reactions.test.ts:271-274` pins this. Failure scenario: a move action whose policy is `all` of 32768 true leaves plus one false leaf evaluates 32769 leaves and returns `rejected invalid_state` with no record. The same action with 32769 true leaves evaluates the same 32769 leaves, faults `budget_exceeded` and writes the record. The work is the same but the outcomes differ, and the content author loses the one diagnostic the observation exists for. 04 §5.4 is not silent here: "Exhaustion returns a typed evaluation fault". The brief allows PM defaults only where the spec is silent, so this default needs one of these:
- (a) One `over({ query_steps: steps.n })` check in `decideWith` that covers a refusal and a non-accepted rule result, so both return the budget fault with its limit. Note that this changes persistence: rejections get receipts at the authority, faults do not.
- (b) A reviewed amendment to 04 §5.4 that exempts rejections ("budgets bind the proposal of an accepted rule result"), recorded by the owner.

The owner or PM chooses. Either one closes B-1.

**N-1 (nit): `observe`'s own transaction is untested.** At `mobile/authority/local-story/trace.ts:60-68`, dropping the `transaction()` wrapper keeps every test green. No failure that changes the game follows: the catch still contains any error, and `trace()`'s `transaction()` runs first and rolls back any leftover open transaction. The only effect is that a crash between the INSERT and the DELETE leaves 1001 rows for one record.

**N-2 (nit): diagnostics files accumulate.** `kernel/ts/test/budget_record.test.ts:52` writes a new `tmp/obs/diagnostics/<uuid>.jsonl` on every run, and `kernel/ts/test/sim.test.ts:105-108` reads every file in that directory. Local runs therefore read more each time. This is the same pattern as `found()`, so it is harmless in CI.

**Q-1 (question): the end-of-adopt order.** At `kernel/ts/src/proposal.ts:56-62`, compose's job limits (via `apply`) are checked before `events`/`output_bytes`. A final proposal over both `events` and `created_jobs` reports `created_jobs`, but §5.4's list puts `events` first. The brief treats these as separate check sites, so this is not a finding unless the PM reads "the same check" as "the end of the proposal".
