## What must be true (from the spec, before the diff)

1. The clock unit is fixed and stated where `LogicalTime` defers to the calendar; a world that
   never moves the clock keeps its bytes and hash (brief, frozen-format rule).
2. `wait` is one explicit advance (04 §5.4) to a time strictly later than now; anything else is
   a rejection that changes nothing. Due-job processing is deferred, and the deferral is visible.
3. A recipe's `duration` is a time cost (21 §7 Cost) that commits on success and on failure;
   a rejection moves no time (04 §5.0).
4. The hour-of-day policy is a pure leaf that reads only the clock from the decision
   environment (01; 04 §4), wraps midnight, and fails closed on a kernel that lacks it (06 §21).
5. The luck check draws from the world's RNG only after every admission check. A failed check is
   an accepted decision with a typed failure outcome, and its draw, time and steps commit. A
   rejection draws nothing (04 §5.0). The same world and command give the same bytes (14 §R5),
   so a retry can replay (03 §14).
6. The event lists of check@1, action_recipe@1 and the clock advance are complete now, so no
   later change under the same version alters an existing lock's events (04 §5.2, #44 F2). The
   check event can serve 00a's `check_passed` objective by a stable check key.
7. The compiler and the loader agree on every new field and cross-check. The format stays
   `loka-cartridge-v2`, additive only; existing fixtures, cartridges and transcripts are
   byte-identical.
8. The command result stays bounded, and a fault is a typed result that discards the whole
   proposal. It is not an exception out of the kernel (04 §5.2 step 7, §5.4).

## PM ruling Q1 (policy versioning), judged

Sound. "A new leaf operator is versioned by its owning capability's lock; a changed meaning
takes a new `policy_version`" fails closed on every older kernel, twice over (schema and lock).
It changes no existing fixture answer: `policy_version: 2` is still `const_mismatch`, and no
existing policy's meaning moves. One wording gap is N2.

## Event streams (#44 F2), judged

- **check@1:** `check_passed` or `check_failed` at position 1 of every accepted perform of a
  checked recipe, before the outcome's steps. Nothing else. Threshold checks (S6b) and later
  check kinds reuse the same two events, since the payload carries no kind. Result bands will
  be new optional `outcomes` keys, so a cartridge without them keeps its events whatever
  "passed" rule bands adopt. Deferring that rule is a non-finding, provided the bands slice
  keeps a success/failure-only recipe's events unchanged.
- **Clock advance:** `wait` and `duration` emit no event. When due jobs arrive, their events
  come from jobs, which need new content (job definitions), so no existing lock's events
  change. N1 covers the recipe side of that.
- **action_recipe@1:** decided, but with a payload gap. See S3.

## Findings

**S1 (should-fix): a schema-valid `wait` makes every later timed perform throw out of
`step`.** `kernel/ts/src/rules/action_recipe.ts:58` computes `add(from, duration)`, which throws
`KernelError('integer_overflow')`. Nothing catches it: `world.ts:187` calls the rule directly.
`wait.until` is `LogicalTime`, an integer with `minimum: 0` and no maximum below 2^53 - 1, and
`schedule.ts` accepts any `until` later than now. Failure (probed): `wait until
9007199254740991` is accepted, and from then on every `perform` of a recipe with a `duration`
throws `Error: integer_overflow` out of `step`, on every attempt, for the life of that save.
The same happens with an authored `duration` of 2^53 - 1 from time 0. The PR's disposition
("content would need a clock or duration near 2^53 seconds") misses the command path: the
player's own client can send the command. This PR is also the first to put throwing arithmetic
(`add`, and `uniform`'s `rng_budget_exhausted`) inside a rule, and 04 §5.2 step 7 makes an
evaluator fault a typed result that discards the proposal, not an exception the host must
guess about. Fix, smallest first: have `decideWith` turn a `KernelError` from the rule into
`{kind: 'fault', code}` (both codes are registered `ErrorCode`s), with one test (`wait` to the
maximum, then a timed perform, faults `integer_overflow` and leaves the world unchanged). Or
bound `until` and `duration` in the schema so that `until + duration` cannot overflow; that
also needs the clock itself bounded, so it is the larger change.

**S2 (should-fix): one check DefinitionRef can name two different checks.**
`protocol/action.schema.json:921` (RecipeCheck `key`) and the check events make `check` a
"DefinitionRef of kind check". Neither the compiler (`lib/loka/content/recipes.ex`) nor the
loader (`kernel/ts/src/cartridge_refs.ts` `recipes`) checks that inline check keys are unique.
Failure (probed: loads): `swim_pool` with `{key: swim, chance: 30}` and `swim_river` with
`{key: swim, chance: 90}` both emit `check: ashmere@0.0.1:check/swim`. A 00a-style objective
`check_passed: checks/swim` then completes on the easy river. More basically, one DefinitionRef
names two definitions, which is exactly what DUPLICATE_DEFINITION exists to forbid (03 §2,
05 §4). When named `checks/<key>` definitions arrive (00a), an inline key equal to one of them
collides a third way. Fix: report DUPLICATE_DEFINITION for a repeated inline check key, in
both the compiler and the loader, with a red case each, and state in RecipeCheck that an inline
check's key is its definition's key. Alternatively, if shared keys are intended for reuse,
state the rule now in RecipeCheck, including how a later `checks/` definition of the same key
is treated. Either way, decide it before an artifact freezes the ambiguity.

**S3 (should-fix, frozen now): `action_completed` fires on a failed attempt and cannot say
so.** `action_recipe.ts:54` emits `{type: action_completed, action, subject_id}` after either
outcome. Its schema (`event.schema.json:357`, `additionalProperties: false`) has no outcome
field. Failure: an author writes the 00a Q3 pattern `event: {type: action_completed, action:
pick_lock}` for "open the crypt". It completes on a failed lock-pick (transcript ordinal 5:
`check_failed` and then `action_completed`, with the gate still shut). No quest can tell the
two apart except through `check_passed`, which a later outcome-without-check (result bands)
would not emit. Adding an `outcome` field later changes the event bytes of every
`action_recipe@1` lock, which is the #44 F2 problem again. Fix, pick one now: (a) emit
`action_completed` only for outcomes `performed` and `success` (existing transcripts are
unaffected, since they are all `performed`), or (b) keep it on every attempt and add an
`outcome` field that only checked recipes carry, so existing bytes stay the same. I recommend
(a), with the event description saying "a failed attempt emits its check event and no
`action_completed`".
If the PM prefers the current meaning, record it in the event's description in those words
("any admitted attempt, failure included; match `check_passed` for success") so quest authors
are not surprised.

**S4 (should-fix, naming against the normative list): the new op is `time_of_day`; 06 §21's
core operator is `time_window`.** `protocol/policy.schema.json:183`. 06 §21 lists
`time_window` among the core policy operators. The op name freezes into every artifact that
uses it. Failure: a builder or the AI factory (08) writes 06 §21's `{op: time_window, ...}`
and gets SCHEMA_VIOLATION. Or R8 adds `time_window` for absolute LogicalTime windows, and the
AST then has two time operators where the normative list has one, with nothing saying which
is which. Fix, trivial now: rename the op to `time_window` (the brief asked for "a window"). Or
have the PM rule that `time_of_day` is 06 §21's `time_window` for hours and record that in
the Policy description with the reserved meaning of `time_window`. Two normative texts
disagreeing is a stop-and-ask (AGENTS.md), so it should not stay silent.

**N1 (nit): the recipe's `duration` advance has no due-jobs pointer.** `action_recipe.ts:56-59`.
Only `schedule.ts` carries the `ponytail:` note. 04 §5.4 makes action time costs explicit
advances that snapshot and run their due set exactly like `wait`. Failure: the schedule slice
adds due-job processing to `wait` only, and a `pick_lock` with `duration: 600` jumps past a
job due in 300 s, silently skipping it (04 §5.4: "may not silently skip jobs"). It also needs
to place job events relative to `action_completed`. Add the same one-line note at the
`time.advance` in the recipe rule.

**N2 (nit): the versioning sentence leaves one case open.** `policy.schema.json:7`: "A new leaf
operator is versioned by its owning capability" does not say what happens when an operator is
added to a capability version that is already installed (for example a second fact op under
fact@1). An older kernel with fact@1 would then fail such an artifact as SCHEMA_VIOLATION
instead of CAPABILITY_NOT_INSTALLED. It still fails closed, but the diagnostic points a repair
loop (08 §6) at the wrong cause. Add: "adding an operator to an installed capability takes
that capability's next version".

## Developer's open questions, ruled

- `duration` has no maximum: S1. The overflow is reachable by command, not only by absurd
  content.
- The "passed" rule for result bands deferred: non-finding (see Event streams).
- `invalid_state` for a `wait` that does not advance time: non-finding. The action is offered
  but its input is not valid in the current state, which is what the code means in 04 §7.
  There is no better registered code.
- `wait` offered to every cartridge locking schedule@1: non-finding. No kernel installed
  schedule@1 before this PR (`INSTALLED` on main has no `schedule` or `check`), so no
  loadable artifact's ActionSet or command outcome changes. `ashmere_hello` locks both but
  could not load before. The GameView offering `wait` is 00 §4.2's explicit wait (04 §5.4:
  R6P uses explicit wait).
- #44 F2 lesson: check@1 and the clock advance are fully decided; action_recipe@1 is decided
  except for S3.

## Composes-with (reviewer step 7)

The statement is accurate. `time_of_day` is an ordinary policy leaf, `duration` and `wait`
share the one `time.advance`, and the check selects existing outcome steps. Capability code
names no content. `COMPOSES = {action_recipe: ['check']}` names another capability, as 21 §7
requires (a recipe's check joins its proposal). The roll lives in the recipe rule. When 00a's
lantern `take` gains its check, containment will need the same roll, and it should move to a
check module then, not before.
