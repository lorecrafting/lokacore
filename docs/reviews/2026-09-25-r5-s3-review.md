## What must be true (from the spec, before the diff)

1. A fact is typed, namespaced and scoped; an unset fact reads its declared default; no helper
   defaults a scope because an id was omitted (03 §6, §7; 21 §4).
2. Facts change only through a registered delta op with a canonical MutationTarget, composed
   under the R3 rules; rules never write state; there is no generic set-field (04 §5.1; 21 §11).
3. A policy is a pure condition tree over committed state (all, any, not, comparisons); an op
   whose capability is not installed fails closed, never evaluates as true or false (21 §3.2;
   14 §R5 "unknown capabilities fail").
4. InspectableDetail keeps its S2 fields and gains `variants` as an optional field; a room or
   detail without variants compiles, loads and hashes as before except for the lock; variants
   are derived from state, never a mutated description, so `look` still commits an empty delta
   (21 §6; 14 §R5 freezes the v1 shape).
5. Variant selection is defined once in the portable projection over committed state; hosts
   render, they do not choose (04 §14, §15).
6. Pre-S3 state hashes and transcripts are byte-identical (a fresh state has no facts entry).
7. The actor comes from the command or the host, never `world.character` inside a rule
   (contract lessons); every new short-reference field is in `expand/2`.
8. Every new `required` and bound has a fixture that fails when removed; known answers are
   computed outside the kernels; where Elixir and TypeScript both check a rule, they accept and
   reject the same inputs.

## Findings

- **F1 (should-fix, before merge) `lib/loka/content/checks.ex:62-65`**: the `exits` clause of
  `expand/2` matches *any* map with an `exits` key. This PR makes the room clause recurse into the
  rest of the room (needed for variant conditions), so it now reaches the room's `details` map.
  A detail keyed `exits` (schema-valid: `^[a-z][a-z0-9_]{0,63}$`) makes the details map match
  the clause, and `Map.update!(["mooring_post", "post", "mooring"], "to", …)` raises
  `BadMapError`: the compiler crashes instead of compiling or emitting a diagnostic. Reproduced
  on a copy of `ashmere_details` with `mooring_post` renamed to `exits`. Regression: on `main`
  the clause returned without recursing, so this content compiled. The loader has no such key
  sensitivity, so a hand-built artifact loads while the compiler cannot produce it. "Exits" is a
  plausible detail name (`look exits`). Fix: match the room shape (for example
  `%{"exits" => exits, "title" => _}`) or expand `to` at the Connection level; add a compile test
  with a detail keyed `exits`.
- **N1 (nit) `kernel/ts/src/cartridge.ts:215, 247-249`**: the fact-reference check over every
  policy tree sits behind the v2 guard, so a v1 artifact (facts, policies and actions only)
  whose action policy compares an undeclared fact loads. Harmless today: no rule evaluates action
  policies. Scenario when S5 does: `holds` reaches `value()`, which reads `.scopes` of
  `undefined` and throws at decision time. Record it for the S5 brief: move the fact check out of
  the v2 guard when action policies are first evaluated.
- **N2 (nit) `protocol/room.schema.json` examples (InspectableDetail, RoomDefinition,
  DescriptionVariant)**: the examples reference `ashmere_facts@0.0.1:fact/bell_rung`; that
  cartridge's fact is `chapel_bell_rung`. Examples are validated for shape only, so nothing
  fails, but an author copying the example into `ashmere_facts` gets UNRESOLVED_REFERENCE.
- **Q1 (question) `kernel/ts/src/world.ts:135-152`, `kernel/ts/src/compose.ts:110-113`**:
  `compose` does not check a `fact.assign` value against the FactSpec, `adopt` runs no invariant,
  and `facts_typed` is test-time only, as `movement.invariants` already are. 04 §5.1 asks for
  final invariant validation over the composed proposal before persistence; 03 §7 forbids an
  untyped bag. Pre-existing pattern, and no rule writes a fact yet, so not a finding on this
  slice. The first fact-writing rule (S4/S5) is where it becomes real: that brief should either
  run `facts_typed` on the fact-assign path in `adopt` or check the value's type in `compose`.
- **Q2 (question) deferred item "fact_changed events"**: `capability_registry.json` gives
  `fact_changed` to `fact@1`, and `admit()` faults `unowned_event` for an event whose owner is
  not the deciding capability. So a `take` rule (containment) that proposes `fact.assign`
  cannot itself emit `fact_changed`. Either the host synthesizes `fact_changed` from the
  composed fact changes (03 §7: "Changing a fact produces a typed fact_changed", which reads as
  a property of the change, not of the rule) or ownership gets a carve-out. For the PM before
  the S4 brief; nothing to change here.

## The eight developer decisions and the two open questions

1. **Scopes player and instance, exactly one per fact, rejected at the TypeScript loader only:
   agree.** 03 §7 allows a set of scopes, but `fact_compare` and `fact.assign` need one scope to
   read or write at, and this kernel has no rule to pick among several; refusing at the loader
   is fail-closed (14 §R5) and the diagnostic text says exactly what the code does. The compiler
   is host-neutral: a party-scoped fact is valid content for a Realm host, so compiling it is
   right. *Open question, should the compiler also reject it for `offline_private` cartridges:
   no, not now.* `supported_profiles` has no semantics in the compiler yet, the loader fails
   loudly inside the author's `loka play` loop, and profile-specific acceptance belongs to Lab
   certification (09), not the compiler. Revisit if party or realm facts ever appear in offline
   content.
2. **Defaults at world init, no facts entry until the first set, changes only via
   `fact.assign` → `compose` → `adopt`: agree.** `factDefaults` is keyed by canonical
   DefinitionRef text, which is exactly what `compose` reads as `fact_defaults` (verified
   against `compose.ts:111`, and mutant M13 dies). The fresh-state test and the unchanged
   transcripts show pre-S3 hashes hold. Exporting `adopt` is safe: it takes only an `Admitted`,
   which only `admit()` makes, and `admit` was already exported.
3. **Ops limited to all/any/not/fact_compare, other ops blocked at the loader: agree.** The
   evaluator's throw is unreachable through `loadCartridge` with `INSTALLED` (an unlocked op is
   UNDECLARED_CAPABILITY, a locked-but-uninstalled owner is CAPABILITY_NOT_INSTALLED); as a
   default branch it fails closed rather than evaluating to false. Strict equality on FactValue
   is right because the compiler already rejects a mistyped `equals`.
4. **First match in list order, base when none holds, chosen at view-build time: agree; this
   is the right freeze.** It is the only deterministic rule that gives the author priority
   without a weight field; the 00a §12 amendment and the schema description both state it, so
   the freeze is written down. Selection in `describe()` from the GameView and the host's detail
   text keeps `look` at an empty delta (21 §6 "prefer derived variants"; 04 §15 one portable
   projection). The trace never records which variant was shown, which is correct: views are
   derived, not decided.
5. **`inspectable_detail@1` required, `description_variant@1` for variants, details hash
   regenerated, `loka-cartridge-v2` kept: agree.** *Open question, keep the tag:* yes. The
   compatibility rule is about shape (optional field additions keep the tag); this is a
   tightened validation on artifacts none of which has shipped, and it fails loudly with
   UNDECLARED_CAPABILITY. A v3 tag would cost a branch in both compiler and loader for no shape
   change. Recorded rule: a tag bump is for shape changes; a check that tightens before any
   artifact ships does not bump.
6. **Ruleless capabilities listed explicitly in `INSTALLED`, feature map counts them
   implemented via `implemented_in`: agree.** A self-declared cell is weaker than "a rule module
   exists", but the two guards close it: `world.test.ts` ties `INSTALLED` to the rule files plus
   the implemented ruleless rows (read from the files), and the new red control proves
   `features.exs` fails on a ruleless row without its cells. Mutant M10 shows the tie works in
   both directions.
7. **Transcript shows only default selection: agree.** No command sets a fact before S4/S5, so
   the transcript cannot show a change without a fake command. The change itself is covered
   through the delta path (`facts.test.ts`: worried → base → celebration, base → flooded, per-actor
   player fact), and the `loka play` test plants a variant that holds at the defaults.
8. **Deferred items: agree, with Q1 and Q2 attached.** `fact_changed`, party/realm scopes,
   other ops, named-policy variants and details in the GameView are each outside this slice's
   spec sections or blocked on a later capability. Q2 says why `fact_changed` needs a design
   note before S4; Q1 says where fact typing must be enforced once a rule writes one.

Lessons: rules take the actor from the command (`describe` takes `actor` as a parameter; the
rule's `decide` uses `world.body` as the S2 lesson records; the GameView and `loka play` pass
`world.character` as the host, which the lesson allows; mutant M3 proves the actor parameter is
honoured). Short refs: the variant condition's `fact` is expanded by the recursing room clause
(E1 dies; the Python known answer confirms the artifact carries full refs), and that recursion is
also what exposes F1.

## Composes-with

The PR's statement checks out. Reads: conditions read any declared fact through one evaluator
(`policy.holds`); descriptions read conditions through one selector (`describe`). Writes: facts
change only through the registered `fact.assign` op in `compose`/`adopt`; there is no
description-mutation path. Any later proposer of `fact.assign` (take/give, ActionRecipe
consequences, quests, reactions) changes every room and detail description that reads the fact
with no extra code, which the tests demonstrate by setting facts through `admit`/`adopt` alone.
Names: `grep` of `kernel/ts/src` finds no cartridge, room or fact name. `RULELESS` names three
capability keys to build `INSTALLED`, which is registry plumbing, not a mechanic special-case.
`policy.ts` dispatches on `fact_compare`, fact@1's registered op: that is the shared vocabulary
of 21 §3.2 (comparisons), not one mechanic naming another. No finding under step 7.

## Verdict

**APPROVE WITH NOTES.** Every item in the list above holds under mutation: facts are typed,
scoped and defaulted; they change only through the delta path; the evaluator is pure and fails
closed; the detail shape is additive and `look` still commits nothing; selection lives in the
projection; pre-S3 hashes are unchanged; both known answers and the state hash reproduce outside
the kernels; the compiler and loader agree on every constructed input except F1. F1 is a
compiler crash on schema-valid content, a regression of this PR's `expand/2` change, and must be
fixed (with a test) before merge; it is a two-line change. N1 and N2 are at the developer's
discretion. Q1 and Q2 are for the PM to carry into the S4/S5 briefs.
