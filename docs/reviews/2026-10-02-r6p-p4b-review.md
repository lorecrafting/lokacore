## Developer deviations

- **The lost-acknowledgement tap holds ROLLBACK until settle**: accepted. Without it,
  `transaction`'s ROLLBACK closes the transaction, and `reconcile` proves the outcome definite
  at once, so `commit_pending`, the fenced `recover` and `settle` could not be expressed. It is
  the same jam pattern as `local_story.test.ts:292-297` and :469-472, and `settle {committed}`
  runs the real COMMIT.
- **The saved state is read with `load()` on a read-only connection, not a restart**: accepted.
  Each `recover` step does a real restart on the same file (:233-237). A hot journal would make
  the read fail, not pass silently. The read-only connection cannot change the file.
- **Quest mutant built as quest-completes-on-take**: accepted as an interpretation of "resolve
  the quest on take". The early-possession mutant above covers the credit side.

## Findings

- **N1 nit** `mobile/authority/local-story/lantern.test.ts:101-104` and :251. `before_commit`
  is a JS throw from the tap, not a SQLite error. The rollback of the partial writes is real
  (see 3), but SQLite's own failure path is not exercised here: for example, SQLITE_FULL that
  has already rolled the transaction back before `rollback()` runs. That path is already
  covered with a real SQLITE_FULL at `local_story.test.ts:221-229`. Also, the bare `catch` at
  :251 maps any throw to `rolled_back`. A non-fault step that throws still fails, because its
  expected result differs, so this is a readability point only.
- **N2 nit** `lantern.test.ts:240`. In `gameView(p.story.world()) && at('accepted', 'observed')`
  the `&&` operand is always truthy, so the result is a constant that the test makes. Under
  the PM's reading-step ruling, `reading-has-no-effect` can fail only through its state and
  durable compares, not its result. This is a consequence of the ruling, not a defect. Calling
  `gameView` and then returning `at(...)` on its own line would make this clear.
