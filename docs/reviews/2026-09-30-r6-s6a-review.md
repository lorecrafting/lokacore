## Requirements derived before reading the diff

1. Kill before COMMIT: reopen shows exactly the prior committed revision (OFF-03).
2. Kill after COMMIT: reopen shows the new revision once; a retry of the same invocation is a
   replay at that revision, no second effect or RNG draw (OFF-04, OFF-05; 03 §14).
3. A storage write failure leaves memory and storage at the prior revision, with a typed or
   thrown recoverable error, never `saved` (OFF-06; 03 §15).
4. A file SQLite cannot read, a corrupt page or damaged head is a typed `save_corrupt`; open
   never invents or re-pins state (OFF-07).
5. View reads, reopen and the host clock never move the `play_time` clock (07 §10, DET-04).
6. The phone trace is bounded: ADR-075 §2 states the cap and the rule at the cap (oldest whole
   other runs go; the current run keeps its replayable beginning).
7. Trace ordinals follow commit order even when a ROLLBACK fails (S2 R2-F1).
8. No test-only code in production modules; failing traces kept as a CI artifact.

All eight are met, except the cap (6) is exceeded on two write paths and its recovery cost is
unbounded (A1-A3 below), and requirement 4 is met at open only for the rows open reads (F1).

## Findings

**F1: should-fix, `mobile/authority/local-story/store.ts:96-97`, `docs/ROADMAP.md` S6a row.**
Scenario: the receipt table's primary-key index page (or any receipt/trace page past the first
row) is corrupt. `openStory` returns `open`; the first `invoke` throws an untyped
`database disk image is malformed` from the receipt lookup (`authority.ts:152`). The PR body's
Open list names it ("deeper pages fail on use") but the ROADMAP S6a row's "Open for S6b" list
names only the repair and the expo wording, and the comment at `store.ts:96` says "the table, not
its index" without saying where the index fails. Fix: one clause in the ROADMAP open list (owner
S6b/SM2), as S3a F3 required for this carry.

**N1: nit, `mobile/authority/local-story/faults.test.ts:198`.** Fault points are any NEW
receipted command, including rejections that change no world state, so the memory half of the
oracle is idle there: memory adopted before COMMIT turns only three of eight seeds red in the
corpus (other suites catch it). Picking points among accepted commands would make every seed
check it.

**N2: nit, `mobile/authority/local-story/faults.test.ts:202`.** The `full` fault's `/./` matcher
is never used (`:215` uses `{ errcode: 13 }`).

### Reviewer's disposition of Astra's findings

- **A1: confirmed, downgraded to should-fix.** Reproduced: trace at the cap, 20 new games, 5020
  rows (headers are 460 B each, written by `catchUp`'s `header`, `trace.ts:89-93`, which never
  calls `room`). Not a blocker: each extra row needs a player-confirmed new game or an app update
  with no command after it, and the next traced command of a new run evicts them all (5020 to 21
  rows in the probe). A capped run does keep one SAVED header per app update forever. Fix: make
  header writes go through `room` too.
- **A2: confirmed by reading `trace.ts:35-46` (room checked once, then up to two rows);
  downgraded to nit.** The overshoot is one row, and the next write evicts or stops, so the
  cap holds within one entry.
- **A3: confirmed by reading `trace.ts:123-135`; should-fix.** Every open of a capped run loads
  every untraced receipt's command and response (about 1 KB each) before `traceCommand` returns
  `capped` on the first. The cap exists to bound the trace's phone cost; this cost grows with
  play past the cap. Fix: check `room` before the receipt scan, or fetch one row at a time.

### Reviewer's note on Astra fix round 1

- **B1: concur, should-fix** (checked by reading `trace.ts:35` and `authority.ts:269-271`; not
  re-run). At 4999 rows the two-row pair is refused as `capped`, `traceAfter` does not set
  `behind`, and the next one-row entry takes the last slot. The trace then skips a committed
  command, so the kept part no longer replays to the saved world: this breaks the ADR-075 §2
  amendment's "replayable beginning". My round-1 APPROVE missed it, because the pair test stops
  after the dropped pair. That APPROVE is withdrawn pending fix round 2.
- **A3: concur in part.** The reread happens only while a run sits below the cap after a refused
  pair. The next open fills the last slot and the run is then `full`, so this is a one-time read,
  not one at every open. It probably goes away with the B1 fix (once a run refuses a write, it
  should count as full).
