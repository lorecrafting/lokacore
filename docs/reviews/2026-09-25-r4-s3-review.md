# Review: R4 S3 — TypeScript cartridge loader (R4 minimal)

PR #26 (`r4-s3-ts-loader`, draft), commit reviewed `0bb540b0256e27ae755fe967ddc15cdf482a6dc6`.
Reviewer: independent (Fable; authored none of the work). Full review: the loader is a trust
boundary. CI green on the head (elixir, typescript, lint, android, ios). Scope: the loader,
its corpus, `CAPABILITY_OWNERS` in `bin/contracts.exs`, the DiagnosticCode text edits. Test 4
(cross-kernel proof with the S2 compiler) is not in the PR and gets a scoped follow-up.

## Verdict: APPROVE WITH NOTES

No blocker, no should-fix. Two nits in the test file, one question for the R6 host wiring.
Every hand-made artifact I built was rejected at the stage the frozen text names, every
correct one loaded with the fixture hash, and nine mutants each failed the suite.

## Must be true (written from the spec before the diff)

1. Stage order and stop-at-first exactly as the frozen DiagnosticCode text at `8558773`:
   size (raw byte length, before any decode) → canonical decode → `cartridge.format` →
   CartridgeArtifact schema → `content_hash` → definition keys → lock against requirements →
   installed kernel/app; the pins re-checked (05 §3; CAR-07 "before any save mutation").
2. `content_hash` = SHA-256 of the canonical bytes of `cartridge` only (05 §11, §20; CAR-05,
   CAR-10; C3). Expected hashes come from Python, never a kernel (AGENTS.md "Writing tests").
3. The decoder is loka-numeric-v1: duplicate keys, floats, lone surrogates, depth over 128 and
   non-UTF-8 bytes are `INVALID_JSON`; 4 MiB is the inclusive cap (owner decision R4 item 2).
4. The lock equals `requires.capabilities` both ways (R4-02), and every command and policy op
   a definition uses has its owner's key in the lock (S1 round-2 note; CAR-07; C4).
5. Definition map keys agree with the manifest's id and version and the definition's key;
   kind is the schema's job (PM Q1).
6. Installed checks: `key@version` present, `kernel_api` in `[at_least, below)` compared
   numerically, `content_schema` and `rule_ir` equal, every client feature present (05 §3, CAR-07).
7. Within a stage the first diagnostic in list order: path, then code, by UTF-8 bytes, then the
   whole (Diagnostic; PM Q3). Paths follow the loader grammar (`.name`, `["…"]`, `[n]`).
8. The code set is closed; the schema edits are description text only and change nothing
   beyond the PM rulings (Q1–Q5, UNKNOWN_COMMAND re-run).
9. Pure kernel code; `canonical.ts`, `sha256.ts`, `validate.ts`, `contracts.gen.ts` reused.
10. Tests name their break, use fixture or hand-written literals, and fail on plausible mutants.

## Checked

- **Requirements 1, 5–7 against the code.** `loadCartridge` runs size → `fromUtf8` + `decode` →
  format → schema → hash → keys → lock → installed, each stage collecting and `first()`
  sorting with `validate.ts`'s `cmp` (code-point order, which is UTF-8 byte order; loader paths
  are ASCII anyway since `decode` rejects non-ASCII keys). The hash is computed before the schema
  stage but reported after it, so the order observed is the frozen one. The three two-fault
  corpus cases and my probes (`installed 0.9` plus `rule_ir 2` → `KERNEL_API_UNSUPPORTED` first,
  `k` before `r`) confirm the list order inside a stage.
- **Requirement 2.** `hash(c)` is `sha256Hex(utf8(encode(cartridge)))`. Recomputed every corpus
  artifact's `content_hash` with Python `json.dumps(sort_keys=True, separators=(",",":"),
  ensure_ascii=False)` + `hashlib`: all 26 decodable artifacts agree (the three deliberate
  mismatches are `hash_mismatch` and the two two-fault cases whose declared value is the
  fixture's), and the fixture's `fe17f082…84f2` recomputes. A declared hash of the whole
  artifact text is rejected (`CONTENT_HASH_MISMATCH`). All artifacts are canonical text except
  `duplicate_key`, which cannot be.
- **Requirement 3.** `fromUtf8` is strict by round trip through `sha256.ts`'s `utf8`; I checked
  the cases by hand: continuation byte as lead, overlong 2- and 3-byte forms, CESU-8 pair,
  lone high surrogate, 5-byte lead, truncated tail all re-encode to different bytes; a lone low
  surrogate re-encodes identically and `decode` rejects it in a string. Above U+10FFFF
  `String.fromCodePoint` throws, caught. Empty input, BOM, depth 129, a scalar document and a
  `cartridge` array all give the right code. The cap test uses 4 MiB + 1 of `0xff` (undecodable)
  and exactly 4 MiB of `0xff` → `INVALID_JSON`, which proves both the inclusive bound and that
  size runs before decode. `TextDecoder` is not available to the kernel (`lib: ["ES2022"]`,
  `types: []`), so the hand-rolled decoder is the right rung; a lenient `TextDecoder` mutant fails.
- **Requirement 4.** Both directions of the lock check (`lock_missing_required`, `lock_extra`,
  and my "same key, other version" probe). Owner coverage: command owner absent from lock and
  manifest → `UNDECLARED_CAPABILITY` with `{capability}` and `[key@version]`; nested op under
  `not` → `all` walked; my `not` → `has_item` probe with `containment` unlocked reports the op
  and does not descend into the DefinitionRef. `UNKNOWN_COMMAND` for a command no capability
  owns, as ruled. `CAPABILITY_OWNERS` is generated from `capability_registry.json` by
  `bin/contracts.exs` (`pin.(e)` per command and policy op), so the registry stays the only
  catalog; `--check` is green in CI.
- **Requirement 8 (schema text).** Word-diffed the DiagnosticCode description against `8558773`.
  Every change is a path/data statement per loader code (Q2), the kind clause removed from
  `ARTIFACT_DEFINITION_KEY_MISMATCH` (Q1), the first-in-list-order rule (Q3), the owner-coverage
  and `UNKNOWN_COMMAND` clauses in the lock stage (brief; PM ruling), and "is not UTF-8 or" on
  `INVALID_JSON`. The enum, the stage list and the compile-time causes are unchanged. Nothing
  beyond the rulings.
- **Requirement 9.** `ast-grep scan --error kernel/ts/src` clean; imports are the four named
  modules only; `check_ts_size.mjs` clean; `cmp` export is the one `validate.ts` change.
- **Mutants (throwaway detached worktree, then restored; baseline 38/38):** swap lock and
  installed stages → 1 fail; drop the UTF-8 round trip → 1; cap exclusive → 1; hash over the
  document instead of `cartridge` → 2; `first` without sort → 1; owner checked against the
  manifest instead of the lock → 1 (`stage_list_order`); policies map not walked → 1;
  capability version unchecked → 1; `TextDecoder` (lenient) for `fromUtf8` → 1. Nine of nine
  killed. Tree clean afterwards.
- **Tests (requirement 10).** Expected values are `cartridge_hash.json` literals and the
  hand-written corpus, read with `JSON.parse`; each case names its break; no mocks, no
  change detectors. The corpus exercises every loader code and every field of
  `ARTIFACT_DEFINITION_KEY_MISMATCH`.
- **Over-engineering.** Nothing to cut. `stages` as an array of thunks is the shortest form of
  "run in order, stop at first"; `apiCmp` on digit strings is right where `Number` could lose
  precision on a 64-digit component; the `ponytail:` on per-character decoding names its limit.

## Findings

### N1 (nit) — one `test` over all 29 corpus cases hides every failure after the first

`kernel/ts/test/cartridge.test.ts:34-41`. `assert.deepEqual` throws on the first mismatching
case, so a regression touching several cases reports one. `for (const c of corpus.cases)
test(c.name, …)` is the same length and names each failing case in the runner output.

### N2 (nit) — the known-answer test's `installed` is looked up by another case's name

`kernel/ts/test/cartridge.test.ts:10-12`. `corpus.cases.find((c) => c.name === 'hash_mismatch')
.installed` couples test 1 to the corpus's naming; renaming or dropping that case makes test 1
throw on `undefined.installed` for an unrelated reason. `corpus.cases[0].installed`, or a
literal, breaks only when the installed shape does.

### Q1 (question) — `Installed.kernel_api` from the host is not validated

`kernel/ts/src/cartridge.ts:199-206`. `apiCmp` assumes `M.m` without leading zeros. A host bug
passing `"1"` throws a `TypeError` from the loader instead of returning a result; `"1.0.0"` is
silently read as `"1.0"`. The value is the host's own configuration, not the artifact, so this
is not the trust boundary the slice guards; noting it for the R6 host wiring, which should
build the value from a constant. No action in this slice.

## Notes (no action required)

- A non-canonical layout of a valid artifact (whitespace, unsorted keys, `/` where the
  schema pattern allows it) loads with the same hash: the profile's parser accepts it
  (numeric-profile.md "Parsing") and the semantic hash is over the canonical bytes of the value
  (05 §11, §20: "not host-specific compiler output bytes"). Consistent with the spec; Test 4
  should compare `encode(decoded)` bytes, as the brief says.
- The `INVALID_JSON` `try/catch` also swallows a programming error in `fromUtf8`; the
  known-answer test bounds that (a broken decoder rejects the fixture).
- `CAPABILITY_OWNERS` keeps the last version if the registry ever lists two versions of one
  key; every key has one version today and Q4 compares keys only (PR body notes it).
- PM rulings challenged: none. Q1 (kind mismatch is the pattern's `SCHEMA_VIOLATION`), Q3
  (first in list order), Q4 (owner key only, events later) and the `UNKNOWN_COMMAND` re-run
  are all the smallest correct readings of the frozen text.
- Test 4 (ADR-074 §3 cross-kernel proof) is not reviewed here; it gets a scoped review when
  PR #27 merges and the developer adds it.
