## What must be true (from the spec, before the diff)

1. `resource.adjust` is checked integer arithmetic in an explicit sequence. Every step checks
   `from` against the current value and `to` against the bounds, and never clamps. Writers in
   different groups on one resource conflict (04 §5.3 row).
2. The current value is derived from a stored value and time (02 §A), with regeneration
   stopping at the maximum. That stop belongs to regeneration, not to an adjustment. A write
   stores the derived value. Both kernels compute the same thing, including at hour boundaries.
3. An unaffordable cost or an active cooldown is a rejection. It draws no RNG, moves no time,
   pays nothing and changes nothing (04 §5.0). An admitted failed attempt pays its costs and
   starts its cooldown, like a success (04 §5.0).
4. The compiler and the loader accept and reject the same artifacts for every new field. No
   schema-valid artifact makes `step` throw (S6a Astra).
5. Event streams: `resource@1` emits nothing. `movement@1`'s and `check@1`'s events are
   unchanged for every existing lock. `movement@1`'s delta changes only under a new lock
   combination (#44 F2).
6. Formats are additive (tag `loka-cartridge-v2`). Changed known answers and transcripts are
   exactly the ones the PM ruling allows, and each is re-derived independently of the kernels.
   `ashmere_hello` (v1) keeps its bytes, and an artifact without `resource@1` loads with no
   pools.
7. Pools belong to the actor's body (`bodyOf`), not to `world.character` (puppeting).

## Findings

**S1 (should-fix): the approved "a step leaving bounds is a fault" rule makes ordinary healing
fault, and no author can prevent it.** `kernel/ts/src/resource.ts:46` computes `to = from + by`,
and compose faults when `to > maximum` (the intended "never clamp"). Recipes cannot read
resources: no policy leaf does, and 06 §21's `resource_compare` is not built. So a recipe with
a positive `resource.adjust` step has no way to be unavailable at full value. Failure (run with
`loka play` on the demo, `cartridges/ashmere_road/recipes/pray.json`):
`e, pray, wait, pray, wait, pray` ends in `(fault: precondition_failed)` at `hp 25/25`, in six
ordinary commands. `resources.test.ts` pins this as intended. However, 04 §5.2 step 7 treats a
fault as a discarded evaluation (budget, conflict, evaluator), not a game outcome. A player who
prays at full health should get a refusal or a successful no-op, not a fault. The behaviour is
correct to the approved design, so this is for the PM to decide. Cheapest spec-native options:
(a) add the `resource_compare` policy leaf (06 §21), so authors can gate a heal and the action
shows unavailable; (b) reject a perform `invalid_state` at admission when a step would leave
bounds, for recipes without a luck check (after a draw a rejection is not allowed, 04 §5.0);
(c) keep the rule, record it as a known limit, and change the demo so that it does not ship a
recipe that faults in normal play. Whichever the PM picks, R7's healing and potions will need
it.

**S2 (should-fix): a schema-valid long cooldown turns the cooldown refusal into
`evaluator_error`.** `kernel/ts/src/rules/action_recipe.ts:99` computes
`add(last, recipe.cooldown)`, and `ActionRecipe.cooldown` (`protocol/action.schema.json:752`)
has `minimum: 1` and no maximum. Failure (probed): the demo with `"cooldown":
9007199254740991` (an author's "once ever"), then `e, wait, pray, pray`. The second pray, with
`last = 3600`, overflows 2^53-1. `decideWith` catches the KernelError, so the player gets
`(fault: evaluator_error)` instead of the `cooldown` rejection. It is contained (nothing
changes, no throw escapes), but it is the wrong result for a valid artifact, the S6a S1 pattern
again. Fix, one line: compare `sub(from, last) < recipe.cooldown`, which cannot overflow for
`0 <= last <= from`. Alternatively, bound `cooldown` in the schema (for example ResourceInt's
maximum), with an invalid case.

**N1 (nit): Elixir `current/3` uses `div` and a strict match, TypeScript uses `Math.floor` and
loose reads.** `lib/loka/core/compose.ex:98-100`. Both agree on every state a path can produce,
where clock and `at` are at least 0. They differ on a negative clock: TS changes the value, while
Elixir faults `precondition_failed`, because `div` truncates toward zero. They also differ on a
stored row without `at`: Elixir raises MatchError out of `compose`, while TS faults. The other ops
never raise on a malformed row. `Integer.floor_div/2` would match the documented
`floor(time / 3600)`, and a non-raising read would match TS's fault.

**N2 (nit): the delta's `resource.adjust` `from`/`to` are plain `integer`**
(`protocol/delta.schema.json:451,454`). The PM ruled 32-bit bounds, and `by`, `difficulty`,
`amount` and the spec fields all use `ResourceInt`. Compose bounds `to` and `from` in effect,
so nothing is wrong today. Tightening the schema after this freeze would be a breaking change,
though, and bounding it now costs two `$ref`s and one invalid case.

**N3 (nit): the branch predates main's #48** (the PM ruling's text, the 00 §4 amendment, and
the #48 line in `docs/reviews/README.md`). This record's README line is appended at the same
place, so merge main before merging the PR.

No blockers. Loader/compiler parity for every new field has red cases on both sides, and the
mutants above confirm them. The fixtures are hand-derived and verified. Both kernels agree on the
new ops.
