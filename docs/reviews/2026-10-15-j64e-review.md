## Findings

1. **Should-fix.** `cartridges/spells_sampler/text.json:20` (`"reason.ward": "Needs level 2"`), pinned by `mobile/app/book/word_bar.test.ts:113`. Failure scenario (probe at this head): after `accept_quest apprentice` and `trace_sigil`, the apprentice reward gives 20 experience. GameView shows level 2, wis 10, 1 unspent point, and `spell_words` ward `{available:false, reason:{code:invalid_state, message:{key:reason.ward}}}`. The Book shows "ward, cast: Needs level 2" to a level-2 player. The ward policy (`cartridges/spells_sampler/recipes/ward.json`: `level_compare` at_least 2, `stat_compare` wis at_least 11) passes the level check and fails the wis check. Spending the unspent point on wis makes ward castable. The PM ruling says one reason covers the whole policy (level or wis), so the text must name both (e.g. "Needs level 2 and wisdom 11"). The TS tests reach the level-1 case only through `levelled(w, 0)` (`kernel/ts/test/spells.test.ts:146,265`). The brief premise ("level 1 after learning ward") does not occur in this sampler.
2. **Should-fix, PM ruling.** `kernel/ts/src/commands/actions.ts:222` (`refusal` returns `refusalReason(...)?.code`, so the command error drops `message`), against brief ACCEPTANCE "casting ward is refused with the same reason". The PR keeps GameError `{code}`, which is spec-consistent: `protocol/error.schema.json:67` says "never English text", and `action.schema.json:876` states "the perform or cast refusal stays invalid_state", and the UnavailableReason description (`gameview.schema.json:1950`) keeps GameError unchanged. "Same reason" therefore means the same code plus the GameView text. Failure scenario: a protocol client that sends `cast ward` gets `{code:invalid_state}` with no text, and words.ts renders it "You can't do that: not now." The Book has no typed cast field, so the Book is not affected. Disposition: the PM accepts this reading, or asks for a GameError data field, which is a second schema change and a scope trigger.
3. **Nit.** `protocol/action.schema.json:876` (ActionRecipe description, the reason clause) says the GameView adds the reason to "the action's" unavailable reason. A refused use-target recipe is hidden instead (`view/use.ts:37` `if (code) continue`), so its reason is never shown. mechanics.md states this limit; the schema text does not.
4. **Nit.** `lib/loka/content/recipe_tips.ex:53`: `reasons/3` sits in a module named for tips. Naming only.

Disposition: findings 1 and 3 are text-only (sampler string, test literal, schema description). Finding 2 waits on the PM ruling. None blocks the contract.
