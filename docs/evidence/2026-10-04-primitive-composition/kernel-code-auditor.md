Declared Core/Content/Runtime Elixir boundaries were inspected structurally, not compiler verified. No xref was run because it could compile.

Governing context: active `docs/system/{architecture,mechanics,protocol}.md`, owner emergence decision `docs/archive/decisions/owner-decision-emergence-2026-09-25.md`, archived catalog `docs/archive/spec/21-composable-world-primitives.md` (normative boundaries, future catalog distinguished), and `docs/world-parameters.md`. ## Findings, ordered by impact

### PC-01 — actual static defect: exit availability bypasses ActionSet composition

`commands/actions.ts:156–171` composes room `subtract`, `intersect`, `replace`, `union`, and `override`. `refusal:190–207` checks the resulting set and actual policies. `content/cartridge_recipes.ts:59–76` admits a room contribution naming the registered `move` command; it does not forbid removing move. In contrast, `view/view.ts:138–170` derives available exits only from scene modality, barrier passage, standing and fare. It never asks whether the actual move is offered or policy-admitted.

Controlled counterexample inferred without executing code: a room with a valid exit, sufficient resource and standing actor declares `{op:"subtract", actions:["move"]}`. The exit remains `available:true` from `view/view.ts:166–170`, while `step` returns `unsupported_capability` from `commands/actions.ts:202`. A cartridge override of move with a false policy similarly produces an available exit and `invalid_state`. Active GameView contract says available exit moves must not be refused with `invalid_state` or `unsupported_capability`; `view/invariants_view.ts:73–81` explicitly includes both. This is a current defect in a shared composition surface, not hypothetical future generalization. Smallest direction: have exit projection reuse the actual admission result for the resolved move/actions, preserving current barrier/position/fare precedence and actual invocation alias semantics. A future implementation must add a behavioral regression for subtract/false-policy and demonstrate a red control. No fix or test was performed in this audit.

### PC-02 — current scaling debt: completed durable occurrences accumulate, and every compose scans them

`mechanics/schedule/rule.ts:31–40` completes an existing job and schedules a new distinct job. `foundation/compose.ts:170–174` retains both completed and pending rows; no deletion or retention operator exists. `compose.counts:114–124` calls `Object.values` and filters the entire jobs section on every compose, including commands with no job operation. Its pending budget bounds only pending jobs, not completed history. `runtime/apply.ts:18–28` copies a whole written section, and `runtime/proposal.ts:166–174` may repeat this as jobs/deliveries read the candidate; `adopt:57–64` counts/recomposes once more. Thus ordinary action work depends on total occurrence history, and a job-bearing candidate copies that history. Recurrence is already consumed by NPC schedules and trusted elapsed; this is concrete scaling debt, not a demand for a generalized job framework. No phone latency, measured regression, budget breach or data loss is claimed. First sustained-recurrence/retention consumer should choose minimum typed retirement/compaction and/or maintained counts, with persistence/replay contracts amended first.

### PC-03 — documented limits of composability, not currently missing arbitrary authority

The available lower vocabulary is real but narrow. Recipes are fixed-detail actions and can request only `fact.assign`, `resource.adjust`, `event.emit` (`mechanics/action_recipe/rule.ts:49–85,145–164`); reactions accept only fact transitions/room entry and assign facts (`mechanics/reaction.ts:26–64`); quest event objectives accept only specific item acquisition (`mechanics/quest/lifecycle.ts:75–94`). A custom emitted event cannot trigger an authored ReactionRule under the current closed schema. Recipe target properties/tags, entity selectors, typed barrier changes, item transfer/spawn/status/damage consequence exposure are not available to builders merely because some corresponding delta exists internally. This matches the installed subsets in active mechanics; it does not satisfy the entire future catalog/emergence aspiration.

Pull a new primitive or consequence with its first actual consumer (e.g. status application needing timed expiry, death needing typed durable health/lifecycle changes, craft needing conserved quantities). Do not express every semantic state as authored facts or expose generic field writes. Preserve the distinction between L1 transactional substrate and L2 mechanical authority. The fact-backed *engine-reserved* position/scene states below are existing specific contracts, not authority to reimplement combat/ownership/etc as unrestricted facts.

### PC-04 — documented orchestration seams with clear generalization triggers

The runtime directly calls quest earned-delivery, schedule rule, and reaction delivery; reaction directly appends scene-start deliveries. These are actual named seams but active architecture/mechanics explicitly disclose them. Generalize the event-start hook when a second capability needs it, rather than make a one-implementation registration abstraction today. Likewise the schedule dispatcher currently recognizes one job kind; add a typed durable job contract/dispatcher when the first other job consumer arrives. Merged code does not implement planned combat/status/population or hardcode a rat ID into an installed writer.

### PC-05 — shared query behavior differs by purpose; do not silently unify semantics

Custody queries are intentionally different: `lookups.reach:33–37` traverses open containers for take/lids; `policy.held:72–75` climbs containment regardless of locked lids for has_item; `target.present:59–64` covers direct room/body entities and room details; `description_variant.decide:16–18` uses direct presence. Worn items are specially inventory-scoped for remove only (`actions.ts:240–248`). A key inside a held locked chest can authorize unlocking because has_item ignores lids (`barrier/rule.ts:10–13` documents this). Nested take is exposed only as the engine take (`view/action_lists.ts:51–64`), not arbitrary alias targeting. These are installed subset limitations and distinct notions of ownership/presence/reach. Do not delete them as redundant until an actual consuming contract asks for a single semantic query; give that query a name and preserve the intended differences.

### PC-06 — existing bounded recurrence limitation is atomic and explicit

A single raw wait/elapsed interval spanning the next newly scheduled boundary faults `nonfuture_job`: schedule computes `next(schedule,row.due_time)` (`schedule/rule.ts:31–39`) but compose requires its newly scheduled due time to exceed the whole advance horizon (`compose.ts:167–170`). `docs/system/mechanics.md:363` states this and requires host boundary segmentation. M1's merged elapsed host segmentation lies outside this kernel contributor's inspected scope; do not call normal elapsed broken from an over-horizon raw step alone. Legacy wait retains this limitation. Failure leaves all world/RNG/time unchanged (`proposal.ts:50–64,92–96`).

## Composition trace and authority ownership

1. `commands/invocation.ts:31–54` validates actor/invocation and derives placement-independent command ID plus canonical intent digest. Resolve79–98 resolves actual ActionSet key, ordered targets and named recipe/quest/continuation to a typed Command. TARGETS57–70 is a command-specific adapter; it is not an arbitrary builder selector.
2. `runtime/world.ts:83–147` routes owned command through cartridge lock, checks trusted world/actor/nil identity, forbids player elapsed and uses a separate schema+derived-ID trusted elapsed path. Admission calls actual `refusal`, with optional selected action key. Unkeyed replay limitation for multiple matching policies is explicitly marked at87–89; do not claim keyed invocation and saved-command replay always equivalent under future aliases.
3. Rules return pure typed ops/events. `runtime/decision.ts:179–199` allows event composition only recipe→check, schedule→movement, dialogue→quest/containment; `proposal.admit:285–290` checks this ownership again. `fact_changed` is host generated after an assign, not an illegal event escape from another rule.
4. `proposal.join:183–208` joins sequence ops and inserts change events in causal slots, correlates to root command, records eligible quest instances at event position. `react:220–248` drains FIFO: earned quest state first, then triggered authored rules and scene starts, each writer group distinct. Policies read candidate state at event logical time. Events from scheduled jobs retain due time and run_job cause but root correlation (`schedule/behavior.ts:64–79`, `proposal:212–217,271`).
5. `proposal.jobs:253–273` snapshots due committed jobs sorted due time/job ID, decides each schedule job against the candidate, remaps writer group, drains its reactions before the next. Existing primitive conflicts between independent writers are fail-closed, even same-value writes. This restricts emergent combinations deliberately; do not silently add additive/coalescing semantics.
6. Lazy prospective `now:166–174` applies only unapplied suffixes; those interim applications do not retain the final overlay writer ownership map. They can evaluate downstream candidates that ultimately conflict with earlier groups. Final whole-delta compose atadopt63–64 rechecks all writer conflicts/expected states, then adopts; no intermediate world commits or persistence occur. Expected-state errors may surface from an interim suffix before the final whole-proposal conflict, so do not promise a full global conflict map during every speculative read.
7. Final adoption validates all authored fact values against FactSpecs, counts aggregate ops/jobs/events/output bytes, composes entire delta once and stamps opened_revision, adopts RNG only on success (`adopt:42–72`). All fault/reject branches retain original world. Whole-world deep-cloning/re-encoding is absent on this path: output_bytes canonical-encodes the **decision**, not the entire world (`adopt:60`). Changed section clones remain actual O(section rows) work.

## Invariant and cross-language scope

`runtime/invariants.ts:149–263` contains the independent observation checks for portable transfer/containment/no-last-writer/preconditions/fault/target order/publication and TS step invariants. World-level movement/fact/containment checks are registered separately (`world.ts:175–180`). They are checks for fixtures/simulation/host observations, not a claim all checks run automatically in step. `unknown_types_fail_closed` validates accepted output only when called; typed production Rule ABI/lint/schema/loading supply ordinary restrictions. This audit did not run those guards or their red controls.

Elixir `lib/loka/core/compose.ex:59–74,136–150` mirrors ordered overlay conflict and atomic changed-row results; target78–99, op152–257, retained-history counts123–130, rows299–303 correspond to TS foundation. BEAM maps structurally share while JS apply copies written object sections. Independent invariant precondition replay is intentionally duplicated in `lib/loka/core/invariants.ex:105–129` and TS invariants183–206: do not delete the independent oracle by reusing compose internals. Legal transition tables are repeated in the independent check for the same reason.

One raw-input robustness difference: TS compose accepts any `typeof clock === "number"` (`foundation/compose.ts:95`), Elixir requires integer (`compose.ex:61`), and independent TS invariant requires integer (`invariants.ts:185`). Fractions/NaN supplied directly as a JS State are not rejected for an empty delta by the TS check. Normal canonical-decoded valid state excludes these values. This is a concrete defensive parity gap below the stated decoded/contract-valid input precondition, not evidence a valid cartridge or save currently produces it. No other cross-language mismatch was established by this bounded read; no differential tests were run.

Core declared deps empty and exports Canonical/Contracts (`lib/loka/core.ex:7`); Content depends Core (`content.ex:21`); empty runtime boundary depends Core/Content (`runtime.ex:7`). No Elixir mechanic twin exists here and no need to build one is implied by portable capability registration under TS-first ADR-074.

## Bounded work versus unmetered collection traversal

Budget counters: policy evaluated leaves, reaction deliveries/depth, op/event/output counts and created/pending/due jobs. Query_steps is not a complete instruction/work counter. It counts a has_item/quest_state leaf as one even when that leaf traverses/looks up many rows. Authored artifact bytes cap4MB and canonical depth128 bound static structures, but do not cap all durable historical sections.

Actual unmetered work to preserve in performance analysis: compose counts all historical jobs114–124; rows scan full containment/quest sections294–299; transfer ancestor climbs256–263; questOf scans instances50–58; policy has_item walks ancestors72–75; reaction scans rules26–37; earned scans/sorts quest instances75–94; resolved rebuilds recipe/action/quest/dialogue sets156–171 and each offer may scan quest rows141–146; detailOf scans all details175–180; target lookup scans all entities/details37–51; view within scans entities once per room/body/slot86–101 and inside scans entities once per displayed container109–120; movement sight scans entities per exit88–96; pending scans choice history55–59. Choice rows also remain after resolution/close; quest history and factual sections have their own retention/growth constraints, not a global instruction budget. Acyclic ancestry is guaranteed by load/compose on valid state; arbitrary malformed cyclic input to reach/has_item is outside this precondition and can loop. None of this establishes latency without measurement.

## Cross-lane confirmation: FactSpec default admission asymmetry

The host/content contributor found the compiler checks enum defaults against their values and int defaults against bounds, while the artifact loader lacks that semantic check. Kernel consequence independently confirmed: `runtime/fresh.ts:59,69–79` adopts declared `value_type.default` into factDefaults; `mechanics/fact.ts:29–31` reads it unchanged; `facts_typed:86–90` checks stored state.facts only, vacuously accepting a fresh world with a bad default. Loader `content/cartridge_refs.ts:158–195` validates referenced policy/assigned values but not the default; `content/cartridge.ts:268–270` checks scopes only. A schema-valid tampered enum or integer default can therefore yield a semantic fact read outside its declaration if loaded. Treat this as a loader/compiler semantic validation asymmetry at artifact admission (host lane owns the finding), not evidence a compiler-produced bundled sampler is invalid. No execution was performed.
