## Requirements derived from the spec (written before reading the diff)

Sources: ROADMAP S1, 03 §§14-15, 07 §§8-9, ADR-072, ADR-075 §4, and the P1 review S-1.

1. The order is: identify (validate, authorize the actor, derive scope and invocation id, compute the intent digest), then the receipt lookup by `(scope, invocation_id)`. Nothing resolves against the current world before the lookup.
2. A matching intent replays the original outcome and its original revision. It does not resolve or decide, and it draws no RNG. An altered intent is an integrity conflict and mutates nothing.
3. Malformed and unauthorized invocations get no receipt. A fault discards its proposal and gets no receipt (ADR-075 §4: fault means unavailable). A terminal rejection may be receipted, with revision, RNG and time unchanged.
4. A new attempt is decided once. Changed rows, revision, clock, RNG and the receipt commit in one real SQLite transaction. The receipt carries the intent digest version. Memory adopts only after COMMIT. A definite failure leaves memory and storage at the prior revision and never reports saved.
5. Commands are serialized, one connection per process, and no host-only API is used in shipped code.
6. The intent-digest bytes and known answers are pinned in a protocol fixture that is computed outside the kernels.

The diff meets 1-6. Items 4 (trace) and the acceptance "consumed choice" are covered by deviations; see S-1 and S-2.

## Findings

**S-1 should-fix: the acceptance "consumed choice" is met by a take stand-in, and this deviation is not recorded.**
- Locations: `docs/ROADMAP.md:62`, `mobile/authority/local-story/local_story.test.ts:81`.
- `choose` resolves as `unsupported_capability` (`kernel/ts/src/invocation.ts:70`), so a choice cannot be the test case. The take covers the ordering.
- A take has no semantic token in `input`, so replay of a continuation-bearing receipt is never exercised through the authority.
- Failure scenario: Gate R6 reads S1 as having proven choice replay, and no later slice owns that test.
- Fix: amend the row to name the slice that makes `choose` admissible as the owner of this test.

**S-2 should-fix: no slice owns the ROADMAP's "required trace".**
- Locations: `docs/ROADMAP.md:62`, `mobile/authority/local-story/authority.ts:47`.
- The effects deferral has a `ponytail:` comment. The trace deferral is recorded nowhere, and ADR-075's local-authority `game_trace` producer is assigned to no S row.
- Failure scenario: S6 "retain failing traces" finds no producer.
- Fix: the PM assigns the producer (S2 or S6) in the ROADMAP.

**Nits**
- N-1 `protocol/residency.json`: the `receipts` responsibility still has no fixtures, so `docs/contracts.gen.md` does not point to `intent_digest.json`. A later Elixir receipts implementation (R14) would find no pinned bytes.
- N-2 `protocol/README.md:14`: the row credits `identity.schema.json` with the intent digest, but that schema does not define it.
- N-3 `mobile/authority/local-story/authority.ts:39`: the conflict check compares digests without the stored `intent_digest_version`. Once v2 exists, every pending v1 receipt reads as a conflict (03 §14). This is harmless while only v1 exists.
- N-4 `kernel/ts/src/known_answers.ts:31`: `attempt` no longer returns the digest. The batched iPhone P1 run must also call `digests()`, or Hermes never checks the intent digest.

## Answers to the developer's questions

1. **The 03 §15 "required diagnostic trace".**
   - My reading: it is the ADR-075 §4 game trace, the only registered trace.
   - ADR-075 §4 records failed and unknown commit outcomes in that trace and calls it "derived, never authority". So it cannot live inside the gameplay transaction; it is written once the outcome is known, and the save needs none of it.
   - No slice owns it (S-2).
   - If the PM reads 03 §15 as requiring the trace in-transaction, the two normative texts conflict. AGENTS.md says to stop and ask the owner in that case.
2. **WAL and `max_page_count`.** The claim is not reproduced.
   - On `node:sqlite` (SQLite 3.53.4), WAL with `max_page_count` clamped gives `SQLITE_FULL` (errcode 13). The S1 suite passes under WAL. Please share the repro.
   - What matters for S2: `max_page_count` fails the statement, never COMMIT, in any journal mode.
   - A deferred foreign-key violation (`PRAGMA foreign_keys=ON`, `DEFERRABLE INITIALLY DEFERRED`) gave a real failed COMMIT under WAL, errcode 787, with the transaction still open (verified).
   - Injecting that fault through a test-created table or trigger is a suggestion only; I have not tested it. Use a child-process kill for the unknown-outcome case.
