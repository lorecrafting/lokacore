## Requirements derived from the spec (written before reading the diff)

From pre-release-proof.md P1 and its evidence section, 03 §14, 04 §§1-3 and §5.0, and ADR-074 §3:

1. The bounded ActionInvocation is validated first. Unknown fields fail before normalization. Malformed and unauthorized requests get no receipt identity.
2. The order is: validate, then authorize the actor against the trusted actor, then derive the scope plus invocation identity, then the intent digest, then (S1) the receipt lookup. Only a NEW attempt is resolved against the current world.
3. The command ID comes from the trusted scope and the invocation_id only, never from client routing or owner fields. It matches the frozen `command_id.json`.
4. The intent digest covers the action key, the actor, the targets in their given order (not sorted) and the validated input, including semantic tokens such as `continuation_id`. It excludes the view-freshness token and transport fields. Its version is explicit.
5. Resolution produces a typed Command. Unknown or unoffered actions fail before the rules run.
6. Rejection, fault and failed attempt stay distinct (04 §5.0). A failed attempt commits its RNG draw. A rejection or a fault leaves the world unchanged.
7. The known-answer corpus runs against the actual adapter. A mismatch reports canonical state and result bytes, not only hashes.
8. The code is portable to Hermes.
9. No frozen fixture or protocol file is changed.

The diff meets 1-9. The only exception is the device half of 7, deferred as described in S-2.

## Answers to the brief

1. **Intent-digest bytes.** They are consistent with 03 §14:
   - the field set is right;
   - `target_ids` are hashed as given;
   - the token is excluded;
   - `continuation_id` is included through `input`;
   - the tag `loka-intent-v1` makes the version explicit.

   Pinning them is **not a blocker for P1**. It should be an **S1 acceptance item**; see S-1.
2. **Deviations.** Both claims hold.
   - Rows 2 and 3 of `command_id.json` have invocation_ids `"story/lineage-1/character-1"` and `""`. These fail the UUID `InvocationId` pattern (`identity.schema.json`), so they cannot pass `identify`.
   - `input_digest.json` is the ADR-075 artifact-bytes digest, not an intent fixture.
3. **Hermes portability.** The type-level guarantee is real:
   - `kernel/ts/tsconfig.json` sets `lib: ES2022` and `types: []`;
   - `bin/kernel_red_controls.sh` plants host APIs and requires `tsc` to reject them;
   - `Object.hasOwn`, `flatMap` and `fromEntries` already appear in `src/`;
   - `structuredClone` and `TextEncoder` appear only in the test.

   Runtime parity on Hermes stays unproven until the device run.
4. **ROADMAP wording.** It does not match the records; see S-3.

## Findings

**S-1 should-fix (for the S1 brief, not P1): the intent-digest contract is pinned only in a test file.** Locations: `kernel/ts/src/invocation.ts:49`, `kernel/ts/test/invocation_cases.json`.
- The command ID has a frozen fixture in `protocol/fixtures/command_id.json` and a `residency.gen.json` entry. The intent digest has neither.
- The intent digest's expected values sit in `kernel/ts/test`, which is outside the frozen-fixture scope trigger.
- Failure scenario: after S1 ships receipts, a later PR changes the encoding and rewrites the expected digests in the same commit, and no scope trigger fires. A pending invocation stored by the old app build then reads as altered intent after an update, which 03 §14 forbids ("must not reinterpret a pending invocation").
- Also, `Identified` does not expose the version, but the 03 §14 receipt has an `intent_digest_version` field. S1 would have to copy the `'loka-intent-v1'` literal into a second place.
- Suggested fix: before S1 merges, move the digest known answers into `protocol/fixtures/`, or state the bytes in 03 §14, and export the version tag.

**S-2 should-fix: the portable corpus cannot show the rejection/fault distinction on the device.** Locations: `kernel/ts/test/invocation_cases.json` (no fault row, no failed-attempt row), `kernel/ts/test/invocation.test.ts:57`.
- The ROADMAP row (`docs/ROADMAP.md:61`) requires that the adapter "on Node and iOS Hermes" matches known answers whose "cases distinguish rejection from fault".
- The fault and failed-attempt cases exist only in the Node-only bell test, which mutates the cartridge.
- Failure scenario: the batched iPhone run passes with 0 mismatches and is then taken as P1's device evidence, while the device never ran a fault or a failed check.
- Suggested fix: add a portable failed-attempt case (the frozen `cartridge_dusk_hash.json` has `pick_lock`, luck 50, with a seed whose roll fails). Otherwise, state in the row that the device run covers identity and rejection only. No frozen cartridge faults, so a fault row may stay Node-only if the row says so.

**S-3 should-fix: the ROADMAP amendment attributes a PM decision to owner words that no record holds.** Location: `docs/ROADMAP.md:61`.
- The row reads "PM brief under the R6 plan approval, paraphrased".
- In this repository, "(paraphrased)" marks the owner's words. `owner-decision-r6-plan-2026-09-30.md` holds only "yes approve" and says "Nothing else is decided". The android-descope record says nothing about when P1's device run happens.
- The change itself is within the spec: ADR-074 §3 asks only for a device sample at R6P, and the android-descope record's "Node plus iOS Hermes" is kept.
- Suggested fix: attribute the change as a PM sequencing decision with its reason, and drop "paraphrased".
- Question for the PM, not blocking: does relaxing the acceptance of an owner-approved P1 row need the owner?

**Nits**
- N-1 `docs/ROADMAP.md:61`: there are two deadlines ("before S3 merges (Gate R6 at the latest)"). Keep one.
- N-2 `docs/ROADMAP.md:61`: "if it fails, rework is limited to P1 and S1/S2" is a prediction written as a rule. Drop it.
