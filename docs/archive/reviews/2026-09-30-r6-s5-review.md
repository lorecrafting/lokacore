## Requirements derived from the spec before reading the diff

- R1. The pending report is written in the same local transaction as the gameplay result (23 §4,
  03 §26). A failed COMMIT leaves no report. An unknown COMMIT settles to "both or neither".
- R2. The report id is stable across retry, replay and restore of one occurrence (23 §4, §11). A
  receipt replay adds no report.
- R3. The binding and delivery state stay out of the canonical gameplay hash (23 §4, 03 §26).
- R4. The binding is recorded in the local queue and checked on upload. A report queued for A is
  never rebound to B (23 §5). The binding belongs to the run ("Story run: ... eventual account
  binding", 23 §5; "immutable account/release binding", 23 §11). It follows 23 §11, "not the
  currently signed-in profile" (10 §31 as amended). A guest run is claimed only by an explicit,
  transactional claim (23 §5).
- R5. Delivery happens outside any transaction. `pending`, `accepted`, `rejected` and
  `needs_attention` are persisted. The response is persisted before acknowledgement. A lost
  response gives no second credit. Nothing is silently dropped. Batches are bounded. No timer is
  the delivery mechanism (23 §4, 10 §31).
- R6. The payload has exactly the MilestoneReport fields: report_id, run_id, release, milestone,
  outcome, observed_revision.
- R7. Save/restart before or after the terminal consequence neither loses nor duplicates the
  milestone (23 §3).
- R8. A new game or reset keeps the reports: completion-at-least-once persists (23 §11; 10 §31).
- R9. An offline completion survives restart and is delivered later through a fake adapter. This
  includes duplicate delivery and account switching (pre-release-proof.md:78).

## Findings

**F-1 (blocker): the binding is the signed-in profile at the milestone, not the run's binding.**
`mobile/authority/local-story/authority.ts:186` (`Host.binding`, `:37`). 10 §31 as amended says
account binding follows 23 §11, "not the currently signed-in profile". 23 §5 makes the binding a
Story-run record and requires a guest claim to be explicit. Failure scenario: a run starts as a
guest (null), the player signs in as A mid-run, then reaches the milestone. The report is bound to
A with no explicit claim, so it silently claims the run. A second scenario: `story_started` is
captured under A, the player switches to B, and `prologue_completed` is captured under B. One run
then carries two bindings, and the server's run association rejects one of them. I agree with
the PM: pin 5's per-milestone capture is overridden by the spec. Suggested shape, not a mandate:
bind once when the run is created (`first()` or `newGame` into `save`), and have each report copy
the run's binding. Reports of a guest run stay null until the R12A claim.

**F-2 (should-fix): one undeliverable report blocks every later report.**
`mobile/authority/local-story/progress.ts:31-40`, ordered by `:28`. Any throw (from `submit`, a
failed validation, or a mismatched answer) aborts the batch, and the same oldest row comes first
on every call. This was demonstrated: with reports bound to A and C pending, a `submit` that fails
only for A (the player is now signed in as C) ran `deliver` three times. C was never sent
(`calls` = `[]`, both rows still pending). That is the account-switch case pre-release-proof.md:78
names: C's completion is starved for as long as A's credentials are missing. Self-review point
(a) is upheld. Lazy fix: catch per row, leave it pending, continue, and rethrow at the end.

**F-3 (should-fix, test gap): pin 1's key match is untested.** `mobile/authority/local-story/milestones.test.ts:155`.
With the mutant, an unmapped `custom_event` (for example a flavour event) mints a milestone
report, and the suite stays green: the `off` case passes no map at all. Zero-code fix: in the
`off` case, pass a map whose only key differs from `bell_rung`.

**N-1 (nit): the report is not validated before commit.** `authority.ts:177-189`. A host map
outcome such as `"Rung!"` is stored and sent as a MilestoneReport that does not conform to the
schema. The map is developer config pending R7, so this is a nit. Self-review point (d): nit.

**N-2 (nit): the `report.lineage_id` column is never read in production.** `store.ts:51`.
`run_id` is already in the payload, so the column could be dropped.

**Q-1 (question, self-review point c): a second emission in one run.** Save/restart duplication
(23 §3) is covered: replay and an unknown COMMIT add nothing (the tests and mutants above). The
bell fixture cannot re-emit: a second ring is rejected with `invalid_state` (probed). Content
emitting a key twice is the R7 compiler's trigger check. Meanwhile, the server's per-run
uniqueness plus `outcome_conflict` → `needs_attention` keep it visible. Not a finding for this
slice.

## Deviations

- Key → {milestone, outcome} map: accepted. It is a marked ponytail, and ROADMAP carries the
  replacement to Early R7/R8.
- Async `Submit`: accepted. Delivery is network-bound, and `bbeaa32` rechecks the open-transaction
  guard after each await.
- New `progress.ts`: accepted. Async delivery is a separate concern from the sync store (52 lines).
- Guest reports wait for R12A: accepted. 23 §5 makes claiming explicit. Rows stay pending and are
  not dropped. This is consistent with F-1's fix.

## Ponytail

No over-engineering beyond N-2.
