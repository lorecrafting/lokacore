The Ferryman’s Lantern, three ways

Three working mockups of the same small model: four places, Bram, one lantern, one barred exit and one choice. Everything works by touch. The Type button opens the text drawer, which takes the same commands. Each compass has a live minimap in its center. The dark shelter is a mockup assumption. The proof spec doesn’t list it, but it shows the LegendMUD rule where you can’t see without light.

Paperback

A book page with tappable nouns. Cards below repeat them, and actions rise in a sheet.

    Reading
    The best of the three. There is one page per place and no scrollback noise, so the eye stays in the prose. Inline nouns keep the “what can I touch” question inside the sentence.
    One hand
    Compass, You and Type sit in the bottom bar, and sheets rise from the bottom. The top of the page is out of reach, but it is only for reading. It needs a mirrored layout for left-handed players.
    Discovery
    Strong. Dotted nouns plus the card strip give two routes to the same target. The weak spot is that what just happened disappears when you move. History lives only in the drawer.
    Access
    Ink on paper is about 13:1. Inline nouns are smaller than 44pt, so the cards are the real touch targets. For screen readers, the inline nouns should be hidden from the accessibility tree and the cards announced as the list. That order is place, prose, result, cards, compass. Dynamic type reflows well.
    Render cost
    The lowest. One text block is replaced per move, nothing accumulates, and no effects run.

    Chip Rail

    A MUD transcript. Every touch echoes as a command, and choices live in the rail.

      Reading
      Good for context, since what Bram said stays just above. It’s worse for immersion because the transcript invites skimming. Old room text is dimmed so the current place stands out.
      One hand
      The best. Tap an entity, then a verb, and neither leaves the thumb zone. Dialogue choices replace the rail instead of covering the page.
      Discovery
      Verbs are always on show, and the › take lantern echo teaches the text drawer for free. The risk is chip overload in busy rooms (crowds, 57 rooms), so it needs grouping and a priority cap.
      Access
      Chips are real buttons with plain labels. The transcript must announce only new entries, or VoiceOver re-reads the log. At large type sizes the rail grows to three rows and pushes the log up, so it needs a cap and a scroll.
      Render cost
      A FlatList append per step is cheap, but memory grows over a session. Cap the log at about 200 entries and virtualize it.

      Lantern Light

      Darkness is the default. Light decides what the page can show.

        Reading
        Lit rooms read like Paperback on a dark page. Dark rooms show almost nothing, on purpose. Darkness is shown by leaving content out, never by low-contrast text: the dim line is still 7:1.
        One hand
        The same as Paperback. Feel around sits mid-page when it is the only thing you can do.
        Discovery
        Hiding things is deliberate here, so there must always be one visible way forward. Without Feel around, a first-time player (the P5 test) gets stuck in the shelter. The minimap shows rooms you have not seen lit as hollow.
        Access
        Screen reader users get “too dark to see” too, which is the same game for everyone. Reduced motion removes the warm fade, and a high-contrast setting should flatten the glow.
        Render cost
        Low. One static gradient layer fades when the light changes, not on every step. In React Native that is an image or an SVG gradient with opacity. Avoid animated blur.

        GameView needs

        These are things the mockups needed from the engine that §4.10 and 04 §15 don’t yet name. The renderer must not work them out itself, because that would mean re-implementing rules.

        1. Unavailable actions with a typed reason. Disabled entries belong in the ActionSet, not missing from it: {action_key, target, enabled:false, reason:{kind: barrier|missing_item|wrong_time|skill|presence|commitment|darkness, text_key, bindings, available_from?}}. This covers the barred west exit, “Row me across” before 14:00, “About the search” without the lantern, and dropping a lantern you promised to carry.
        2. Exit projection per direction. Each direction needs a state (open | blocked | locked | hidden_found | none), the destination label only if discovered, and the blocking reason. The compass badges and screen-reader labels (“West, barred: the causeway is under the tide”) are built from this.
        3. Prose anchors. Room and result text arrive as text_key + bindings, but tappable inline nouns need spans that map to target IDs, for example rich segments [{text}, {text, target_id}]. Without them the client string-matches names, which breaks under localization.
        4. Visibility and light. Each room needs a visibility of lit | dark with a source (daylight, carried, fixed). Obscured entities need a perceived name (“something brass”) and an opaque target handle, so the real ID or name doesn’t leak while it’s dark. Entities also need status tags such as lit.
        5. Map layout for the compass minimap. Discovered rooms need grid coordinates (x, y, z), known edges including blocked stubs, the current room, and seen-lit flags. The §4.10 map lists names and exits but not positions.
        6. Action ordering and roles. Each action needs a priority, a group (social, item, move, meta), and which action is primary (tap) and which is examine (long-press). This keeps the 2–6 sheet and the rail chips the same order on every client.
        7. Dialogue view. This covers the speaker, current line, choices with reasons (item 1), discovered topics for this NPC with a new flag, and a way to close without mutating anything. It also needs the presence rule result when the NPC leaves mid-conversation.
        8. Scene view. This covers beats, the current beat, choices with a one-line consequence summary, and flags for dismissible (“Not yet”) and skippable. Stale choices get a typed rejection that tells the player why (the lantern is gone, Bram has left).
        9. Result narration separate from description. Each ActionInvocation outcome needs its own narration keys (“You lift the lantern. Oil sloshes inside.”), plus quest updates and granted topics as typed change notes. Then the UI can show “Quest updated” or “New topic” without diffing state.
        10. Clock. The view needs the current time for display, plus available_from on time-gated reasons so a “Wait until 14:00” action can be offered.
        11. Text aliases per target and action. The drawer builds suggestions, “which one?” lists and touch echoes (› take lantern) from the GameView. ACT-07 requires an alias to exist, but the view has to carry it.
